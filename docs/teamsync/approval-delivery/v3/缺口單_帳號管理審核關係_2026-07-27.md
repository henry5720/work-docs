# 缺口單：系統管理－帳號管理原型「審核關係」無後端可接

> 對象：PM。日期：2026-07-27。
> 原型：[teamsync-group-tags-settings.html](./prototype/teamsync-group-tags-settings.html)
> 依據：後端 `docs/superpowers/specs/2026-07-09-review-module-design.md`（r1–r4 Approved）、
> `docs/superpowers/specs/2026-07-12-custom-table-approval-gate-design.md`
> 前端契約對照：`teamsync-frontend` → `frontend/src/app/modules/review/docs/backend-contract-map.md`

## 一句話結論

原型「帳號管理」頁的**審核關係區塊**（直屬主管／主要・次要職務代理人）與其衍生的清單欄位、篩選、批量設定，
**後端完全沒有對應資料與 API，本期無法實作，建議先駁回**。
同頁其他部分（基本資料、組織與權限、資源配額）以及「群組標籤」頁，本期可交付。

## 為什麼不是「前端再想辦法」

後端審核模組的設計是**刻意**只認一種審核者：群組。

- spec 開篇定調：審核者一律組成可重用的 **review group**，關卡通過條件是「群組要求」的布林運算式。
- 使用者主檔（`users`）**一行都沒動**。審核模組所有資料表都是新開的 `review_*`。
- spec 的「未來再做」清單（v2 candidates）列了 M-of-N 門檻、代理轉簽、逾時升級、草稿重送——
  **沒有列動態角色／主管關係**。這個需求從未進入後端規劃。

也就是說：「誰是誰的主管」這筆資料，系統目前**沒有任何地方存**，也沒有任何 API 寫得進去。

## 「開一個只有一個人的群組」可以代替嗎

分兩種，結論不同：

| 需求 | 可行？ | 說明 |
| :-- | :-- | :-- |
| 「指定張經理簽」 | ✅ 可以，已是現行做法 | 建一個只有張經理的群組，UI 上顯示成人名，使用者看不到群組概念 |
| 「送給**申請人的**主管簽」 | ❌ 不可以 | 「主管」是隨申請人變動的。群組成員是寫死的，設了張經理就是全公司都送張經理 |

第二項為什麼繞不過去，兩道牆：

1. **一張表格只綁一條流程**，流程的關卡在送單時原封不動複製一份（後端 rule config `template_id` required、
   一張表最多一條審核規則）。沒有「看誰送的再換審核者」這個機制。
2. **就算有，也不知道要換成誰**——主管關係資料不存在。

（另一條死路：靠即時改群組成員來換主管。後端明訂群組編輯**永不**影響已啟動的關卡，
且名單在關卡啟動時就凍結，這樣改會污染所有引用該群組的流程，還有併發問題。）

- 後端強制階層：**不得把任何人的權限設成等於或高於自己**。
- 系統保留的虛擬管理者帳號不可修改。

## 三個可行方向（請 PM 選）

### 方向 A：本期照後端做法出貨（建議）

「主管審核」用**手動維護的群組**表達。例如替每個部門建一個「XX 部主管」群組，
流程關卡選該群組。管理者需自行維護成員。

- 成本：管理者要維護群組；主管異動時要記得改。
- 限制：**一條流程無法依申請人自動分流**。若各部門主管不同，需**每個部門一條流程**，
  各自綁到該部門的表格。
- 好處：本期可出貨，零後端依賴。

### 方向 B：把「動態主管」降級成「明確指定人」（可與 A 併行，**已有**）

「指定張經理簽」＝建一個成員只有張經理、名稱就叫「張經理」的群組。這其實已被方向 A 涵蓋，
且流程編輯器的審核者下拉已有 inline「＋新增群組」捷徑（前端 ADR 0005），
就地建立並自動選入本關卡，不必跳去系統管理。所以 B 的增益是**便利性，不是新能力**。

⚠️ **不要做「自動、無感地替使用者建單人群組」**：

- 後端 `ReviewGroup` **沒有**可區分「個人代理群組 / 真群組」的欄位（只有 name／description／
  created_by／member_ids／時間戳）。
- `GET /groups` 只有 `skip`／`limit`，**沒有任何 filter、沒有名稱搜尋**。
  因此前端無法在伺服器端篩掉這些群組；改在前端過濾會**弄壞分頁與總筆數**
  （一頁 20 筆藏掉 12 筆 → 畫面只剩 8 筆，total 也錯）。
- 每個關卡挑一次人就長一個群組，同一人被多條流程指定就出現多個同名群組，群組標籤頁會被淹沒。

**採取的做法**：維持「管理者有意識地建立、自己命名」。清單上會出現「張經理」這類單人群組，
但它是**可讀的資料**，不是系統垃圾，收拾方式與一般群組相同。
若日後數量偏多，再考慮「挑人前先重用既有同一人群組」的去重（需掃過全部群組，成本不低，暫不做）。

**乾淨解（併入方向 C 的缺口單）**：請後端替 `ReviewGroup` 加一個「個人代理群組」標記
＋ `GET /groups` 的 filter 參數，前端即可把它們從群組標籤頁隱藏、只在挑人 UI 出現。改動很小。

### 方向 C：升級後端，真正做動態角色（另排期）

要請後端加的東西（**不需要動使用者主檔**，符合後端把審核資料獨立的設計）：

1. 一張審核模組自有的關係表，存「某人的主管／代理人是誰」，含「確認無主管」的狀態。
2. 關卡條件新增一種審核者類型：「申請人的主管」等動態角色。
3. 在既有的「關卡啟動時算出實際審核者並凍結」流程裡，多一種查法（查關係表而非查群組成員）。
4. fallback 規則：查不到人時要「不可送出／改送備援群組／跳過此關」——**這需要 PM 定案**。
5. （小項，來自方向 B）`ReviewGroup` 加「個人代理群組」標記 ＋ `GET /groups` 加 filter 參數，
   讓單人群組可從群組標籤頁隱藏、只在挑人 UI 出現。

前端已有 disabled 佔位，後端補齊後開啟即可。

**建議**：A + B 本期出貨，C 開缺口單排後端，不阻擋本期。

## 需要 PM 回覆的問題

1. 方向 A/B/C 的取捨？本期是否接受「主管審核用手動維護的群組」？
2. 若接受 A：跨部門情境用「每部門一條流程」是否可接受？管理成本由誰承擔？
3. 「帳號到期日可編輯」是否本期必要？（要開後端 endpoint 缺口單）
4. 方向 C 的 fallback 規則要哪幾種？（影響後端資料模型，越早定越好）
5. 群組「已套用位置」本期只顯示「套用於 N 條審核流程」（不含表格）是否可接受？

## 備註：與其他缺口的關係

原型「審核關係」缺口與流程設定頁的**動態角色 + fallback** 是**同一個根因**——
後端沒有主管／代理人關係模型。兩者應合併成同一張缺口單處理，不要分開排。
前端現況與其他待辦見 `teamsync-frontend` → `frontend/src/app/modules/review/docs/flow-settings-status.md`。
