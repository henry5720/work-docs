# 審核否決規則比較

- Status: Discussion Draft
- Scope: Review 關卡的核准條件與否決規則
- Purpose: 協助 PM、前端與後端統一「否決」的產品語意

## 一句話摘要

現有後端把「否決」當成一張反對票，與核准一起交由 AND／OR 條件樹計算；PM 則把「否決」視為一票否決權，任何審核者否決都應立即結束整關。

兩種模型都合理，但適用情境不同：

- 現有後端較接近一般投票或共識決策。
- PM 規則較接近企業簽核與風險把關。

## 後端現況

### 條件規則

| 模式                      | 通過條件       | 失敗條件       |
| :------------------------ | :------------- | :------------- |
| 群組內 `any` 任一人核可   | 任一成員核准   | 所有成員都否決 |
| 群組內 `all` 全員核可     | 所有成員核准   | 任一成員否決   |
| 群組間 `OR` 任一群組通過  | 任一群組通過   | 所有群組都失敗 |
| 群組間 `AND` 所有群組通過 | 所有群組都通過 | 任一群組失敗   |

現有後端使用三態 Boolean Tree：

```text
核准     = true
否決     = false
尚未決定 = unknown
```

例如：

```text
OR(false, true, unknown) = true
```

因此在「任一人核可」的群組中，即使 A 已否決，只要 B 核准，群組仍會通過。

### 群組內範例

設定為「任一人核可」：

| A    | B        | C        | 結果     |
| :--- | :------- | :------- | :------- |
| 否決 | 尚未決定 | 尚未決定 | 繼續等待 |
| 否決 | 核准     | 尚未決定 | 通過     |
| 否決 | 否決     | 否決     | 失敗     |

設定為「全員核可」：

| A    | B        | C        | 結果     |
| :--- | :------- | :------- | :------- |
| 核准 | 尚未決定 | 尚未決定 | 繼續等待 |
| 核准 | 核准     | 核准     | 通過     |
| 核准 | 否決     | 尚未決定 | 失敗     |

### 群組間範例

設定為「庫存群組 OR HR 群組」：

| 庫存群組 | HR 群組 | 整關結果 |
| :------- | :------ | :------- |
| 失敗     | 等待    | 繼續等待 |
| 失敗     | 通過    | 通過     |
| 失敗     | 失敗    | 失敗     |

也就是一個群組失敗後，另一個 OR 群組仍可核准救回。

## PM 期待的規則

### 條件規則

| 模式                      | 通過條件       | 失敗條件                         |
| :------------------------ | :------------- | :------------------------------- |
| 群組內 `any` 任一人核可   | 任一成員核准   | 任一成員否決，整關立即失敗       |
| 群組內 `all` 全員核可     | 所有成員核准   | 任一成員否決，整關立即失敗       |
| 群組間 `OR` 任一群組通過  | 任一群組通過   | 任一群組內有人否決，整關立即失敗 |
| 群組間 `AND` 所有群組通過 | 所有群組都通過 | 任一群組內有人否決，整關立即失敗 |

PM 規則應理解成：

```text
核准 → 交由 AND／OR 條件判斷
否決 → 不進入條件樹，直接結束整關
```

因此 AND／OR 只回答「核准票是否足夠」，不再回答「整關是否失敗」。

## 投票比喻

### 現有後端：一般投票

```text
核准     = 贊成票
否決     = 反對票
未操作   = 尚未投票
```

系統收集贊成票與反對票後，再按照 `any`、`all`、AND、OR 規則計算結果。

例如規則是「任一人核可」：

```text
A 投反對票
B 投贊成票
→ B 的贊成已滿足條件
→ 最後仍然通過
```

### PM 規則：具有否決權的審核

```text
核准     = 投一張贊成票
否決     = 按下停止按鈕
未操作   = 不表態，等待其他審核者
```

例如：

```text
A 按下否決
→ 審核立即停止
→ B、C 不能再用核准救回
```

最簡單的差異是：

> 現有後端把否決當成「反對票」；PM 把否決當成「緊急停止按鈕」。

## 為什麼產品面可能需要調整

本產品定位是審核模組，而不是意見調查或多數決投票。審核者按下否決通常代表：

- 發現內容錯誤。
- 發現法規、財務或資安風險。
- 明確拒絕承擔放行責任。
- 要求申請人修正後重新送審。

如果否決仍能被其他人的核准蓋過，可能出現：

```text
財務：發票不完整，否決
主管：核准
群組間 OR：最後通過
```

產品風險如下：

| 問題           | 說明                                   |
| :------------- | :------------------------------------- |
| 用語不符       | 按鈕叫「否決」，最終結果卻不一定被否決 |
| 風險被掩蓋     | 有人明確指出問題，其他核准仍可放行     |
| 責任不清       | 稽核紀錄出現否決，但最終結果是通過     |
| 使用者預期錯誤 | 使用者通常會認為「否決」代表流程停止   |
| 通知矛盾       | 否決原因已通知，後續流程卻又通過       |

如果保留現有後端行為，按鈕名稱更接近「不同意」或「反對」；如果按鈕維持「否決」，則一票否決更符合一般審核語意。

## 未操作不等於否決

「沒有意見」與「否決」必須區分：

| 審核者意圖               | 對應行為                                           |
| :----------------------- | :------------------------------------------------- |
| 同意放行                 | 核准                                               |
| 明確發現問題，不允許放行 | 否決                                               |
| 尚未決定                 | 不操作，維持待簽                                   |
| 不需要由自己決定         | 不操作，等待其他審核者                             |
| 明確棄權                 | 若產品需要，應另定義「棄權／跳過」，不能用否決代替 |

在「任一人核可」模式下，某位審核者不操作不會阻止其他人核准：

```text
A 不操作
B 核准
→ 關卡通過
→ A 的待簽票失效
```

在「全員核可」模式下，不操作會讓流程繼續等待，因為設定本來就要求每位成員核准。

## 群組條件是否仍有意義

採用 PM 規則後，群組條件不會完全失效，但 AND／OR 只剩下核准語意。

例如：

```text
核准條件：庫存群組 OR HR 群組
否決規則：任何人否決立即結束
```

代表：

- 庫存群組或 HR 群組任一方滿足核准條件，即可通過。
- 任何群組的任何審核者否決，整關立即失敗。

尤其當所有群組都是「任一人核可」，且群組間也是 OR 時：

```text
任何一人先核准 → 通過
任何一人先否決 → 失敗
```

此時群組劃分在結果判斷上的作用會大幅降低，主要只剩下指定哪些人具有審核資格。

## 可選產品方案

### 方案 A：固定採用 PM 規則

```text
通過條件：可設定 any／all／AND／OR
否決規則：固定為任一否決立即結束
```

適合所有流程都屬於財務、法務、資安等風險把關情境。

### 方案 B：關卡層級可設定否決規則

| 否決規則         | 行為                                                    |
| :--------------- | :------------------------------------------------------ |
| 依通過條件判定   | 保持現有後端行為；否決視為反對票，交由條件樹計算        |
| 任一否決立即結束 | PM 規則；任何 `denied` 直接讓整關失敗，外層 OR 不能救回 |

畫面概念：

```text
通過條件
├─ 群組內：任一人／全員
└─ 群組間：AND／OR

否決規則
├─ 依通過條件判定
└─ 任一否決立即結束
```

否決規則應設在整個關卡，而不是個別群組，因為 PM 要求否決穿透群組內與群組間兩層。

## 必須確認的副作用

以下組合會使第一個有效決定者可能直接決定整關結果：

```text
通過條件：任一人核可
否決規則：任一否決立即結束
```

結果是：

```text
第一個人核准 → 通過
第一個人否決 → 失敗
```

併發時應以第一個成功完成終局結算的決定為準，關卡結算後的其他決定失效。PM需要明確認可此時序效果，不能同時要求「任一核准立即通過」、「任一否決立即失敗」，又宣稱結果不受送出順序影響。

## 後端影響摘要

### 固定改成 PM 規則

| 範圍              | 影響                                   |
| :---------------- | :------------------------------------- |
| 決定結算引擎      | 收到 `denied` 時直接讓關卡與流程失敗   |
| Boolean Tree      | 保留，只計算核准條件                   |
| DB／API／模板格式 | 不一定需要修改                         |
| 測試              | 需要更新 `any`、OR、巢狀條件與併發情境 |
| 既有流程          | 行為會全面改變，是主要產品風險         |

### 否決規則可設定

| 範圍                                 | 影響                                             |
| :----------------------------------- | :----------------------------------------------- |
| Schema／Enum                         | 新增關卡層級否決規則                             |
| 模板                                 | 保存每一關的否決規則                             |
| Process snapshot                     | 建立送審單時凍結規則，避免模板異動影響進行中流程 |
| ReviewGate                           | 保存實際套用的否決規則                           |
| Decision engine                      | 根據規則選擇條件樹計算或全域否決                 |
| API／OpenAPI／前端型別               | 需要同步更新                                     |
| Notification／Webhook／表格 consumer | 終態仍是 approved／rejected，通常不需改資料形狀  |
| 測試與文件                           | 兩種規則都需覆蓋與說明                           |

整體而言：

- 固定改成 PM 規則，程式改動較小，但既有流程語意改變的風險較高。
- 否決規則可設定，改動範圍中等，但可保留現有流程行為，產品彈性較高。

## 待 PM／後端確認

1. 「否決」是普通反對票，還是一票否決權？
2. 所有流程都採同一規則，還是每個關卡可以選擇？
3. 是否接受「任一人核可＋任一否決」可能由第一個決定者直接結算？
4. 既有模板與進行中流程是否必須保留現有後端行為？
5. 若保留現有行為，UI 是否應將「否決」改稱「不同意／反對」？
