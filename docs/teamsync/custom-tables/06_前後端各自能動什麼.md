# 前後端各自能動什麼：Custom Tables 的職責分界

> **對象**：RD／PM（尤其是「我想改變 AI 的行為，該去哪裡改」的人）
> **目的**：把 Custom Tables 相關的每一個可動之處分成三層，並給一個決策流程
> **對應版本**：teamsync-backend `5.7.2`（`f19ce7af2`）／teamsync-frontend（`bffd65693`）
> **撰寫日期**：2026-08-10
>
> 前一份 [05](05_AI聊天室怎麼用資料表.md) 講「它怎麼跑」，這份講「哪一段是誰的」。

---

## 一句話

**機制是後端的，內容是前端的。**

後端決定「有哪些工具、怎麼運作、什麼時候載入」；
前端決定「AI 看到什麼、能碰哪些表、什麼會被擋下來」。

實務上最有價值的推論是：**AI 選錯表、漏填欄位、寫進壞資料這幾類問題，
幾乎全部落在前端這一半**——不需要等後端。

---

## 三層分界

| | 層 | 內容 | 改動成本 |
| :--- | :--- | :--- | :--- |
| **A** | 後端寫死 | 工具實作、agent 架構、prompt、確認機制、權限演算法 | 發 PR 給後端 |
| **B** | 前端設定 | jobs、grant、tag、系統勾選、`agent_enabled`、persona | 呼叫既有 API |
| **C** | 前端宣告 | schema、欄位、`required`、rules、command 定義與 description | 改 contract／IaC 後重佈建 |

> 💡 **C 是槓桿最大的一層，也是最常被忽略的。**
> `get_instructions` 的**格式**是 A，但它的**內容**幾乎 100% 來自 C。

---

## A. 後端寫死，前端碰不到

| 項目 | 出處 |
| :--- | :--- |
| 有哪些工具、叫什麼名字、怎麼實作 | `custom_tables.py` `_append_access_tools` |
| 工具的條件式掛載規則（有讀權才給 analyze、有 attachment 欄才給 blob 工具…） | 同上 |
| `job → toolkit` 的分派 | `components/agents/tool_loader.py` |
| 每個 job 注入的 protocol prompt | `src/prompts/jobs/*.txt` |
| 兩層 agent 架構（主 agent 拿不到低階查詢工具，必須委派 `analyze`） | `custom_table_analyst.py` |
| 子 agent 的時間錨點是 UTC | 同上 |
| `get_instructions` 的輸出**格式** | `custom_table_read_tools_mixin.py` |
| 兩段式寫入確認、payload 逐位元組比對 | `custom_table_write_confirmation.py` |
| 通用寫入的前置驗證邏輯（未知欄位／必填／型別） | `custom_table_tool_writes.py` `_prevalidate` |
| 權限解析、SCP floor、`acting_chatroom_id` 釘房 | `crud/custom_tables.py`、`crud/custom_table_scp.py` |
| command 服務憑證（`CUSTOM_TABLE_COMMAND_SERVICE_TOKEN`） | 部署層環境變數 |
| rules 的可用型別與語法 | `crud/custom_table_rules.py` `RULE_TYPES` |

**這些連改的介面都沒有。** 想動就是提需求。

## B. 前端能設定（開關類）

| 項目 | 決定什麼 | 前端現況 |
| :--- | :--- | :--- |
| **`jobs`** | 掛哪些 toolkit + 注入哪些 protocol prompt | ✅ 有 API；**選單缺 `custom_table_commands`** |
| **chatroom grant** | 哪些聊天室能碰這張部門表、`scope_values` 是什麼 | ✅ 已在用 |
| **tag 切分** | 哪張表屬於哪個「系統」 | ✅ IaC／tag API |
| **系統勾選（insight flip）** | 已 grant 的部門表要不要載入 agent | ✅ v1 有 UI；chatV2 沒有 |
| **`agent_enabled`（逐支 command）** | 這支 command 給不給 AI 用 | ✅ 已在用 |
| **persona `instruction`** | 取代該輪的 `chatroom.instructions` | ✅ 唯一的提示詞介面 |

### 兩個實務註記

**`agent_enabled` 是被低估的工具。** 庫存模組 19 支 command 裡刻意有 5 支設 `false`
（`link_review` × 2、`mark_needs_review` × 2、`smoke_probe`）——這些是給前端流程用的，
不該讓 AI 自己去呼叫。**「哪些能力給 AI」是一個可以逐支決定的設計選項**，不是全有全無。

> ⚠️ command 的 PUT 是**整包覆寫**，漏帶 `agent_enabled` 會被後端重設回預設 `true`。

**persona instruction 是 B 層唯一能碰到 prompt 的地方**，但它取代的是聊天室層的
instructions，**不會**覆蓋 job 注入的 protocol prompt。想讓 AI「不要用低階工具繞過
command」，靠 persona 寫規則的效果遠不如把 `custom_table_commands` job 打開
——因為那句話本來就在 protocol prompt 裡，只是沒被載入。

## C. 前端宣告 —— 直接決定 AI 看到什麼

### C1. 會出現在 AI 眼前的

| 你宣告的 | AI 那邊看到 |
| :--- | :--- |
| 表名 | `### c29bb5cd_異動紀錄` |
| 表 description | 表名下一行；**沒填就整行不出現** |
| 欄位名 + 型別 | `` `帳務時戳` (datetime) `` |
| `required` | `` `帳務時戳` (datetime, required) `` |
| link 欄 | `` `涉及倉庫` (link → 'c29bb5cd_倉庫' [8ca7f8f7-…], many) ``<br>← AI 靠這行知道表跟表怎麼接 |
| rollup／lookup／formula | 標型別 + 摘要，並在 Rules 段明說唯讀 |
| command `name` | 工具名 `custom_table_command_<slug>_<id8>` |
| **command `description`** | **就是 tool description**——模型唯一看得到的用途說明（≤1024 字元） |
| command `inputs` 的 `description` | 參數說明 |
| command `outputs` 的 `description` | 回傳值說明 |

> 💡 **schema 命名就是 prompt engineering。** 這些每一輪都在模型眼前，
> 比事後在 persona 裡補規則有效得多——後者會被稀釋，前者不會。

### C2. AI 看不到，但會擋住它

| 你宣告的 | 效果 |
| :--- | :--- |
| `required`（且**不配 `default_value`**） | 通用寫入漏填 → 可讀的 `Column 'X' is required` |
| `unique` | 重複鍵擋掉 |
| `transition` | 狀態機白名單，非法轉移擋掉 |
| `immutable_when` | 條件成立後該欄不可改 |
| `check` / `compare` / `require` | 值域與跨欄條件 |
| `exists` / `not_exists` | 關聯存在性 |
| `no_overlap` | 時段不重疊 |
| `require_approval` | 轉成待審核，不直接寫入 |
| `invariant` | **principal-blind 的列形狀規則**——見下方「進階」 |
| `channel` | per-acting-room 的 link 目標收斂——見下方「進階」 |
| command 的 `steps` | 多表原子寫入的實際邏輯 |

### C3. 兩個要一起記的陷阱

1. **`required` 配了 `default_value` 就失效。** 判定條件是「required 且 `default_value is None`」。
   給了預設值不但不擋，還會替漏填的資料寫進一個看起來合理的假值。
2. **既有表翻 `required` 會被擋**，只要還有任何一列是 NULL。
   所以這道防線要嘛建表時就設好，要嘛先清乾淨舊資料。

## 決策流程：「我想改變 AI 的行為」

```
你想達成什麼?
│
├─ 「讓 AI 看得到某張表 / 某支 command」
│     → B 層。查 jobs → grant → tag → 系統勾選 → agent_enabled
│       （壞掉時的完整順序見 04）
│
├─ 「讓 AI 更容易選對表 / 選對工具」
│     → C1 層。改表名、補 description、把欄位名寫清楚
│       ⚠️ 不要跑去 persona 寫「請使用 XX 表」——那是在 B 層補 C 層的洞
│
├─ 「讓 AI 選錯 / 漏填時不會造成壞資料」
│     → C2 層。required、unique、transition、invariant
│       ★ 這是唯一不依賴模型行為的方向
│
├─ 「讓 AI 能做一件多表原子的事」
│     → C 層寫 command + B 層開 custom_table_commands job
│       （兩者缺一都等於沒有）
│
└─ 「改工具的行為 / 改 agent 架構 / 改 protocol prompt」
      → A 層。提需求給後端
```

---

## 常見的誤判

| 誤判 | 為什麼錯 | 該去哪 |
| :--- | :--- | :--- |
| 「AI 沒用 command，是模型不聽話」 | command 有**四個**獨立開關（job／`agent_enabled`／tag+讀權／服務憑證），任一沒過就是零工具，症狀跟「模型忽略工具」完全一樣 | 先做工具盤點（見 05） |
| 「在 persona 裡寫規則就好」 | persona 不覆蓋 protocol prompt，而且離模型的注意力比 schema 遠 | C1／B |
| 「關掉系統勾選就等於撤權」 | 勾選與 job 都只是**視野**，有 grant 的人照樣能用 REST 讀 | grant／row ACL（A 的演算法 + B 的資料） |
| 「AI 讀不到部門表，是後端的問題」 | 三道關卡全在 B 層 | grant → job → 系統勾選 |
| 「加了 command，AI 自然會用」 | 還要 job；沒 job 連「不准繞過」那句 protocol 都沒載入 | B |
| 「讓模型選對工具」當成一個工作項 | 這既不在 B 也不在 C——**它不是一個能做的事項** | 改成「給它選項」(B) 或「選錯也不壞」(C2) |

最後一列是這份文件最想講的一句：
**能做的只有兩種——把選項給它，或讓選錯也不會壞。**

## 進階：`channel` 與 `invariant` 實際上是什麼

這兩個 rule 型別的名字容易誤導，先講清楚它們**不是**什麼。

### `channel` ≠ 「只准命令通道寫入」

它是 **per-acting-room 的 link 目標收斂**：
一張表上一條 channel rule 指名一個 link 欄，允許的目標 id 集合由
**該房 grant 上的 `scope_values`** 決定。

> 動機案例（模組 docstring 原文）：部門擁有倉庫／商品／異動，
> 每個聊天室只能讀寫**它自己那批倉庫**的異動。

庫存模組已經在用它做倉庫收斂。**它跟「誰寫的」無關，只跟「寫進去的列指向哪些倉庫」有關。**

### `invariant` = principal-blind 的列形狀規則

> 「這張表的一列必須合法，**不管是誰寫的、從哪寫的**」

三個特性：無 principal（連 trigger 寫入與審核 replay 都會觸發）、
authoring 時無 scope 限制、**只看 post-image**（不做 pre-image 檢查，
否則規則上線前的舊列會永久不可編輯）。

每張表上限 4 條，與 channel 分開計算。

### 🔴 更正：「帳表僅命令通道寫入」目前表達不出來

`HANDOFF_V5.md` 把這件事列為「待 SCP v1.3 語法確認」的 release gate，
並寫成用 `channel` 達成。**依 2026-08-10 讀 code 的結果，這條路不成立**：

- `channel` 管的是 link 目標範圍，不是寫入者身分。
- `invariant` 是**刻意** principal-blind 的——區分寫入者正是它明確排除的事。
- policy 語法裡沒有任何 `principal_kind` / `via_command` 之類的概念。

**能表達的是「列的形狀」，不是「誰寫的」。**
所以要防「AI 用通用寫入建出算不出結存的單」，可行的方向是把**列的合法性**寫死
（`required`、`invariant` 的列形狀條件），而不是禁止某個寫入管道。

## 現況缺口彙整（前端這一半）

| 缺口 | 層 | 後端有沒有擋 |
| :--- | :--- | :--- |
| job 選單沒有 `custom_table_commands` | B | ❌ 沒有——無 property 前置需求、不互斥，`PUT jobs` 原本就吃它。**純粹是選單少一個選項** |
| chatV2 的 job 選單另缺 `custom_tables_department` | B | 同上 |
| chatV2 沒有系統勾選 UI | B | 端點存在，只差畫面 |

三條都是「後端已經備好、前端還沒接」。
