# AI 聊天室怎麼用你的資料表：從開關到工具的完整流程

> **對象**：RD／PM（想知道「AI 到底怎麼知道要用哪張表」的人）
> **目的**：把「一句話問 AI」到「資料被讀或被寫」之間的六站走完，標出每一站的開關與失敗點
> **對應版本**：teamsync-backend `5.7.2`（`f19ce7af2`）／teamsync-frontend（`bffd65693`）
> **撰寫日期**：2026-08-10
>
> 這份補 [04_AI讀不到怎麼查.md](04_AI讀不到怎麼查.md) 的另一半：
> 04 是「壞掉了照這個順序查」，這份是「正常運作時它是怎麼跑的」。

---

## 一句話總結

**AI 不會「發現」你的表。它在每一輪對話開始前被組裝出一套工具，
然後靠 `custom_tables_get_instructions` 吐出來的一份文字清單認識這些表——
表名、描述、欄位名、型別、哪些必填、你的權限。**

所以「AI 選對表」不是模型的靈感，是**你的表名與欄位命名寫得夠不夠清楚**。
這件事在 schema 設計期就決定了，不是上線後調 prompt 能救的。

---

## 全景：六站

```
使用者說一句話
   │
   ├─① 組工具箱 ──── 房間的 jobs 陣列決定掛哪些 toolkit
   │                  （tool_loader.py 的 job 分派）
   │
   ├─② 決定視野 ──── scope → grant → 系統勾選 → 逐表解權限
   │                  結果是 accessible_tables
   │
   ├─③ 認識這些表 ── get_instructions 吐一份 Markdown 清單給模型
   │                  ★「AI 怎麼知道用哪張表」的答案在這裡
   │
   ├─④ 讀 ────────── 主 agent 只能查 id；真正的分析委派給子 agent
   │
   ├─⑤ 寫 ────────── 兩段式確認，payload 由伺服器釘住
   │
   └─⑥ command ───── 另一個 job、另一套工具、另一組開關
```

①②⑥ 是**設定**（做不對就整條不通），③④⑤ 是**執行時行為**。

## ① 組工具箱：`jobs` 陣列是插槽

聊天室有一個 `jobs` 欄位（逗號分隔字串），`tool_loader.py` 逐個 job 分派，決定掛哪些 toolkit。
跟 Custom Tables 相關的有四個：

| job | 掛什麼 | 工具名稱前綴 |
| :--- | :--- | :--- |
| `custom_tables` | 聊天室**自有**表 | `custom_tables_*` |
| `custom_tables_department` | **部門**表（grant 分享進來的） | 同上 |
| `custom_table_commands` | 把 command 當工具 | `custom_table_command_*` |
| `custom_api_tools` | 自訂 API 工具 | `custom_api_*` |

### 兩個表 job 是「同一個 toolkit 的兩個 scope」

前兩個**不是兩套工具**。它們共用一個 `CustomTableToolFactory`，
`scopes_for_jobs()` 把兩個 job 折成一個 scope 集合：

```python
if str(ChatroomJobType.CUSTOM_TABLES) in jobs:            scopes.add("chatroom")
if str(ChatroomJobType.CUSTOM_TABLES_DEPARTMENT) in jobs: scopes.add("department")
```

**實務後果**：從 AI 列出的工具清單**看不出你開了幾個表 job**——
名字都是 `custom_tables_*`，開兩個只是視野變大。要判斷得去看 `jobs` 本身。

> ⚠️ 一個表 job 都沒開的呼叫者（legacy auto-detect、測試直接建構）會拿到**兩個 scope**。
> 這是刻意保留的 pre-split 行為，所以「沒開 job 卻讀得到」不一定是 bug。

### 工具是條件式掛載的

不是固定一組。實際掛哪些取決於權限與 schema：

| 工具 | 掛載條件 |
| :--- | :--- |
| `get_instructions`、`cheat_sheet` | 永遠（內部使用者） |
| `analyze`、`find_records` | 任一表 `can_read != none` |
| `list_attachable_blobs`、`view_attachment` | ↑ 且**任一可存取的表有 attachment 欄** |
| `insert_record` | 任一表 `can_insert` |
| `update_record`、`delete_record` | 任一表 `can_edit != none` |
| `bulk_record_actions` | 可寫可改 **且非外部客戶**（batch 帶 `changed_by`，外部客戶沒有那個身分） |
| `apply_permission`、`use_passphrase` | 只有外部客戶、且該表沒有完整權限時 |

所以**看到幾支工具本身就是診斷資訊**。例如一個內部使用者的房間列出這 8 支：

```
custom_tables_get_instructions   custom_tables_cheat_sheet
custom_tables_analyze            custom_tables_find_records
custom_tables_insert_record      custom_tables_update_record
custom_tables_delete_record      custom_tables_bulk_record_actions
```

可以直接讀出：讀寫改都有、是內部使用者、**而且沒有任何一張表有 attachment 欄**。

### 每個 job 還注入一段 protocol prompt

`JOB_PROTOCOLS` 把 job 對應到 `src/prompts/jobs/*.txt`，組進系統提示。
這些檔案就是 AI 的使用守則——例如 `custom_tables_protocol.txt` 規定
「所有資料問題一律委派給 `analyze`」「寫入前一定要跟使用者確認」
「`scp_*` 開頭的錯誤是終局，不准換工具繞過」。

**沒開 job = 沒有工具，也沒有那段守則。** 兩者一起消失，這點在 ⑥ 會變得很關鍵。

## ② 決定視野：一張表要過四關才進 `accessible_tables`

```
第 1 關  scope        jobs 決定去撈 chatroom 表 / department 表 / 兩者
第 2 關  grant        （只有部門表）有沒有分享給這個聊天室
第 3 關  系統勾選      （只有部門表）它的 tag 有沒有被這個房間翻開
第 4 關  逐表解權限    resolve_effective_permissions，沒有任何存取就剔除
```

### 第 3 關的規則不直覺

`_insight_allowed_table_ids()` 的判定是：

> 一張已 grant 的部門表會載入，若它**沒有任何 department-scope tag**（untagged → 永遠載入），
> 或它**至少一個 tag 有這個房間的翻開紀錄**。

**「沒 tag」等於「永遠載入」，不是「載入不了」。** 想讓一張表可被開關，得先把它放進某個 tag。

### 第 4 關會釘住「這個房間的」grant

內部使用者解權限時帶 `acting_chatroom_id=chatroom_id`：

```python
resolve_effective_permissions(db, table.id, user_id, acting_chatroom_id=chatroom_id)
```

沒有這個釘子的話，同時在 A、B 兩房的人在 A 房會拿到 B 房的權限（取最寬那筆）。
**釘子只會收窄，不會放寬**——只靠別房 grant 才拿得到的表，在這裡直接掉出去。

### 一個貫穿全部的原則

程式碼註解寫得很直白：

> the scope decides only WHICH TABLES the analyst can see; every level, row filter and
> hidden column is still resolved per-table below, so **a scope can only remove a table
> from the toolkit — never widen access to one**.

換句話說：**① 和 ③ 是「視野」，② 和 ④ 是「安全邊界」。**
關掉視野不等於撤權——有 grant 的人照樣能用 REST API 讀到。
**永遠不要拿 job 或系統勾選當安全機制。**

## ③ ★ AI 怎麼知道要用哪張表

答案是 **`custom_tables_get_instructions`**，它的 description 就寫著
「CALL THIS FIRST before any other custom_tables tool」，protocol prompt 也再叮嚀一次。

它回傳的是一段 **Markdown 純文字**，每張可存取的表一節：

```markdown
### c29bb5cd_異動紀錄
（表的 description，如果有填）

- **Table ID:** `e7df2406-858e-482c-a976-84a50f73d48d`
- **Columns:** `單號` (string, required), `異動類型` (select), `帳務時戳` (datetime, required),
  `涉及倉庫` (link → 'c29bb5cd_倉庫' [8ca7f8f7-…], many), `現有量` (rollup: sum of …), …
- **Your permissions:** can_read=all, can_insert=True, can_edit=all
```

**模型就是靠這段文字挑表的。** 它沒有別的資訊來源——不會去看你的 ERD、你的 PRD、你的前端畫面。

### 所以這幾件事直接決定 AI 選不選得對

| 你寫的東西 | 對 AI 的意義 |
| :--- | :--- |
| **表名** | 最主要的線索。`c29bb5cd_異動紀錄` 看得懂，`tbl_002` 看不懂 |
| **表 description** | 沒填就整行不出現——等於少一個判斷依據，而且是最便宜的那個 |
| **欄位名** | 同上。中文欄名完全 OK，引擎存的是內部 id，顯示名會反向映射回來 |
| **`required` 標記** | **會直接印在欄位後面**。AI 看得到哪些必填 |
| **link 欄** | 印出目標表名、目標 table_id、cardinality——AI 因此知道表跟表怎麼接 |
| **computed 欄** | 標成 rollup/lookup/formula 並附摘要，同時在 Rules 裡明說「唯讀，絕不可寫」 |

> 💡 **這是這份文件最實用的一句話：schema 的命名就是 prompt engineering。**
> 表名與欄位名寫清楚、description 填好、該 required 的設 required，
> 比事後在系統提示裡補一堆規則有效得多——因為前者每一輪都在模型眼前，後者會被稀釋。

### 兩個容易誤解的點

- **權限是「現在」的**：protocol prompt 特別花一整段講「A Pending Permission Application
  NEVER Blocks You」——模型必須以**這一次**呼叫回來的權限為準，不能拿前幾輪的對話當證據。
- **table_id 優先，表名是備援**：Rules 第 1 條要求優先用 table_id；
  名稱唯一時也可以解析，但**絕不能自己編一個 id**。

## ④ 讀：兩層 agent

主 agent **拿不到**真正的查詢工具。低階讀取工具全部包在 `custom_tables_analyze` 這個
**ReAct 子 agent** 裡面：

| 主 agent 直接呼叫 | 只有 analyst 子 agent 能跑 |
| :--- | :--- |
| `find_records`（純 id 查找）、寫入工具、command 工具、blob 工具、`cheat_sheet` | `query_records`、`aggregate_records`、`profile_column`、`correlation`、`join_aggregate`、`traverse_links` |

主 agent 要做彙總／join／統計，**只能把問題本身委派**給 `analyze`，不能自己下 filter。

`join_aggregate` 要有 2 張以上可存取的表才掛；`traverse_links` 要真的有一條
link 連著兩張可存取的表才掛——**工具存不存在本身就在告訴模型它能做什麼**。

### 兩個會咬人的地方

- **時間錨點是 UTC**：子 agent 的 prompt 開頭注入 `CURRENT DATE (UTC)`。
  UTC+8 的使用者早上問「今天」，解出來是前一個日曆日。
- **計算欄位不能篩選排序**：rollup/lookup/formula 的值不落地在 record JSON，
  拿 `json_extract` 去篩會靜默錯。引擎會擋並回可讀的錯誤，但設計 schema 時就該預期。

## ⑤ 寫：兩段式確認，payload 由伺服器釘住

寫入不是「模型呼叫工具就寫下去」。流程是：

```
1. 模型呼叫 insert/update/delete，不帶 confirmation_token
   → 伺服器【不寫任何東西】，把提案（kind / table / record / canonical payload）
     存進 session state，回傳提案 + 一次性 token
2. 模型把提案講給使用者聽，拿到明確同意
3. 模型帶著【完全相同的參數】+ token 再呼叫一次
   → 參數與釘住的提案逐位元組比對（canonical JSON），
     有任何漂移（多一欄、值不同、換一筆記錄）→ proposal_mismatch，重來
```

**為什麼要做到這種程度**，註解裡有真實案例（2026-08-02 staging）：
使用者只要求改「數量」，模型在確認後那一次呼叫**順手把「金額」也改成自己算的
單價×數量**，下游所有彙總跟著錯。結論是

> what the user approved and what executes must be **THE SAME OBJECT**,
> pinned server-side, never re-composed by the model.

> ⚠️ 這層需要 Redis（`ToolkitStateManager`）。沒有時會 **fail-open 退回舊的
> prompt-level 確認**並記 log——不會擋住寫入，但保證也就沒了。

### `required` 在這一層被檢查

通用寫入工具在送出前有一支 `_prevalidate`，會擋下三類問題：不認識的欄位、
**缺必填欄**、型別／格式／長度不合。缺必填的訊息是可讀的
`Column 'X' is required`，模型看得懂也補得回來。

判定條件是「**required 且沒有 default_value**」。

> 🔴 **所以 `default_value` 會把這道防線關掉。**
> 想用 required 擋住 AI 漏填，就**不能**同時給預設值——給了不但不擋，
> 還會替漏填的資料寫進一個看起來合理的假值。這是「宣告面能做的最便宜的防呆」，
> 但只有不配 default 才成立。
>
> 另外：**既有表翻 required 會被擋**，只要還有任何一列是 NULL
> （`_column_has_null_or_missing_values`）。所以這個防線要嘛開表時就設好，
> 要嘛先清乾淨舊資料。

## ⑥ command 當工具：另一組完全獨立的開關

command 不屬於 `custom_tables_*` 那個 toolkit。它有自己的 job、自己的 factory、
自己的工具命名。

### 工具名稱不是 command 名稱

```python
_TOOL_PREFIX = "custom_table_command_"
# custom_table_command_<slug 前 40 字>_<command id 前 8 碼>
```

所以叫 `inventory_reserve_outbound` 的 command，在模型眼裡是
`custom_table_command_inventory_reserve_outbound_a1b2c3d4`。
**用 command 原名去問模型「你有沒有這支工具」會得到否定答案**——
要問前綴，或直接請它列出全部工具。

### description 就是 tool description

command 的 `description`（上限 1024 字元）**是模型唯一看得到的用途說明**，
`outputs` 的每個 description 也會併進 schema。這兩處要寫成「給模型看的使用說明」，
不是「給人看的備註」。

### 一支 command 要露出來，四個條件全部要成立

| 條件 | 出處 |
| :--- | :--- |
| 房間的 `jobs` 有 `custom_table_commands` | `tool_loader.py` 的 `elif job == …` 分派 |
| `agent_enabled = True`（預設就是 true） | `_commands()` 的查詢條件 |
| command 的 tag 有效，且它引用的**每一張**表你都 `can_read` | `_is_visible()` |
| 部署有設定服務憑證（`CUSTOM_TABLE_COMMAND_SERVICE_TOKEN` + service URL） | `_configured()` |

scope 解析是三層 fallback：房間自己的 command → 同部門的 → 同公司的。

### 🔴 最後那個條件是靜默的，程式碼自己承認

```python
# SILENT-OFF ALARM. Without the service credential this factory emits no tools
# at all, so a room whose authors published commands gets an agent that simply
# cannot see them — indistinguishable, from the outside, from "the model
# ignored the tool". Diagnosing it on staging took a dedicated agent probe.
```

所以看到「AI 沒用 command」時，**「模型選錯」是最不可能的解釋**，要先排除：
job 沒開、憑證沒設、tag 無效、引用表沒讀權限。後端有針對這個情境的 warning log。

### protocol prompt 才是「不要繞過」的那道守則

`custom_table_commands_protocol.txt` 明說：

> - Use a command only when its name and description match the user's intent.
> - Surface validation or permission failures plainly. **Do not work around them
>   by calling lower-level table tools.**

**這段守則跟工具一起載入、也一起消失。** job 沒開的時候，模型不只沒有 command，
連「不准用低階工具繞過」這句話都沒看到——它會理所當然地用通用寫入去做本該
由 command 原子完成的事，而且完全不覺得有問題。

## 現況落差（讀 code 讀出來的，官方文件沒有）

| 落差 | 影響 |
| :--- | :--- |
| **前端兩份 job 選單都沒有 `custom_table_commands`**（`JobsSelector.jsx` 11 個選項、`chatV2/…/jobOptions.ts` 10 個） | **command 完全無法從畫面開啟**。而後端 `validate_jobs` 只檢查 enum 與互斥，這個 job 沒有任何 property 前置需求、也不互斥——**現有 `PUT jobs` 端點原本就吃它，缺的純粹是選單裡的一個選項** |
| `chatV2/…/jobOptions.ts` 另外還缺 `custom_tables_department` | chatV2 的房間連部門表都開不了 |
| Insight system 開關（`GET/PUT /private/chatrooms/setting/custom-table-tags/{id}`）在 v1 有 UI（`CustomTableSystemsSelector.jsx`），**chatV2 沒有** | 同一個房間在兩個版本的設定能力不一致 |
| 寫入確認層在缺 Redis 時 **fail-open** | 靜默退回舊行為，只留 log |
| command 服務憑證未設時 **靜默無工具** | 症狀與「模型不理工具」完全相同，只能靠 log 或工具盤點分辨 |

> 04 那份寫「兩份 job 選單都只有 8 個、缺 4 項」——**已過時**。
> `JobsSelector.jsx` 後來補進了 `custom_tables_department` 與兩個 `*_booking_v2`，
> chatV2 補了兩個 `*_booking_v2`。**`custom_table_commands` 是兩邊都還沒補的那一個。**

## 怎麼自己驗證：工具盤點

最快的診斷不是讀設定，是**直接問 AI**：

```
列出你目前可以使用的工具名稱清單（只列名稱，不要說明）
```

拿回來的清單對照 ① 的條件表，可以一次讀出：開了哪些 job、有沒有讀寫權限、
是不是外部客戶、有沒有 attachment 欄、command 有沒有載入。

**這比翻設定畫面可靠**——設定畫面只顯示前端有選項的那些，而失敗點恰恰常常
落在「前端沒有選項」的那幾個。

---

## 對設計的啟示

1. **schema 命名是 prompt engineering。** 表名、欄位名、description 每一輪都在模型眼前。
2. **`required` 是最便宜的防呆，但不能配 `default_value`。** 而且要在建表時就設。
3. **要 AI 做多表原子操作，就得用 command，而 command 目前只能靠 API 開 job。**
4. **不要用 job / 系統勾選當安全機制。** 它們是視野，grant 與 row ACL 才是邊界。
5. **診斷順序永遠是「設定 → 曝露 → 模型」，不是反過來。** 三個靜默失敗點
   （job 沒開、憑證沒設、Redis 沒有）的外顯症狀都跟「模型不聽話」一模一樣。
