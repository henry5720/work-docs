# 設計時的三個決定

> **對象**：要開始設計 schema 的 RD／PM
> **目的**：把「動手前必須決定、而且決定錯了很貴」的三件事講清楚
> **對應版本**：teamsync-backend `5.7.1`（`328f7817`）
> **撰寫日期**：2026-08-04
>
> 📖 **這頁只講「有這件事、會影響你怎麼決定」。精確的 payload、錯誤碼、數值上限一律去官方文件查**：<https://docs.customtable.teamsync.com.tw/zh-TW/>

---

## 一句話總結

**動手前要按順序決定三件事,而且第二件不可逆:**

```
① 哪些表要「一起被同一個動作寫入」  ← 先分組
② 這一組放哪一層（scope）          ← ⛔ 建了不能改
③ tag 怎麼切                      ← 決定 command 邊界 + AI 看得到什麼
```

**順序不能反。** 最常見的錯誤就是先決定 ②（憑直覺「主檔往上、交易往下」），結果 ① 做不到。

---

## 決定一：哪些表要「一起被寫入」

先問一個問題：**你的系統裡,有哪個動作會同時改到兩張以上的表,而且不能只成功一半?**

典型例子：

| 動作 | 同時改到 |
| :--- | :--- |
| 下訂單 | 訂單主檔 + 明細 + 庫存 |
| 認領時段 | 時段（標記被佔）+ 案件（填上負責人） |
| Lead 轉商機 | 客戶 + 聯絡人 + 商機 + Lead（標記已轉換） |

這種動作要寫成一支 command（= stored procedure,見 [01](01_心智模型.md) 第 5 節）才有原子性。

而 command 有一個硬限制：

> **一支 command 只能碰「同一個 tag 底下」的表,而 tag 不能跨 scope。**

所以：

```
✅ 要一起原子寫的表  →  必須同 scope、同 tag
```

**這一組就是你的「系統邊界」。** 先把它圈出來,再往下決定放哪一層。

### ⚠️ 為什麼「主檔往上、交易往下」是錯的

直覺會想這樣切：

```
部門層   ：建案、業務、驗屋師、班表、時段   ← 主檔，大家共用
聊天室層 ：案件                          ← 交易資料，這個群組自己的
```

關聯方向是合法的（案件 → 時段,由窄往寬 ✅）。**但「認領」會爆掉**：

```
認領 = 更新時段(標記被佔) + 更新案件(填負責人)，必須同時成立
            ↓
      時段在部門層、案件在聊天室層
            ↓
      不同 scope → 同一支 command 碰不到 → 被拒絕
```

沒有原子性,兩個人同時按「認領」就會搶到同一個時段。

**所以決定一勝過直覺。** 圈出來的那一組要整組放同一層。

## 決定二：這一組放哪一層（scope）

### 白話:就像公司共享磁碟的資料夾

```
📁 全公司共用/          ← company：幣別、稅率、產品分類
   📁 業務部/           ← department：部門維護，可以分享給好幾個群組用
      📁 A 專案群組/    ← chatroom：只有這個群組在用
```

**放在誰的資料夾裡,決定誰看得到、以及能不能分享出去。** 就這麼簡單。

### ⛔ 但跟 Windows 資料夾不一樣:建了不能搬

這是整個 Custom Tables 裡**最不可逆**的決定。

更新表的時候只能改名字和說明,**沒有任何欄位可以改 scope**。

| 想做的事 | 可行嗎 |
| :--- | :--- |
| 把聊天室的表改成部門的表 | ❌ 沒有這個操作 |
| 把部門表搬到另一個部門 | ❌ 沒有這個操作 |
| 分享給別的聊天室／部門 | ✅ 可以,但**表不會搬家**（見下） |

唯一的補救很貴：把 schema 匯出成 IaC 文件 → 換掛載點重新套用 → **資料自己搬** → 重接所有關聯欄位 → 重建權限、規則、觸發器。

> **所以這一節要在建表前讀完,不是出問題再讀。**

### 三層的實際差別

| | **chatroom** | **department** | **company** |
| :--- | :--- | :--- | :--- |
| 誰的資料 | 一個聊天室 | 一個部門 | 整間公司 |
| 能分享給別的聊天室嗎 | 只能反向分享給部門 | ✅ 可以分享給多個聊天室 | 全公司本來就看得到 |
| **能「同一張表,不同聊天室看不同列」嗎** | ❌ | ✅ **只有這層** | ❌ |
| 現成的表格模組打得開嗎 | ✅ | ❌ 只能自己刻頁面 | ❌ 只能自己刻頁面 |
| AI 讀得到嗎 | ✅ 開 1 道關 | ✅ 但要開 3 道關 | ❌ **完全讀不到** |

> 🔴 **company scope 的表 AI agent 讀不到。** agent toolkit 的 scope 常數只有兩個
> （`CT_SCOPES_ALL = {chatroom, department}`,`custom_table_tool_constants.py`）——
> 沒有 company。所以「全公司共用的基準資料」如果要讓 AI 查得到,得放 department 再分享。

### 對「人」和「對 AI」不一樣

| | 人 | AI agent |
| :--- | :--- | :--- |
| **聊天室表** | 表格模組直接就能用 | **1 道關**：開 `custom_tables` job（UI 上叫「任務：智慧資料表」） |
| **部門表** | ❌ 表格模組打不開,只能自己刻頁面 | **3 道關**：grant + `custom_tables_department` job + 系統勾選,而**最後兩道前端還沒有畫面** |

> ⚠️ **聊天室表對 AI 反而是最簡單的,部門表才最麻煩。** 這跟直覺相反 ——
> 「要給 AI 用所以要放 department」是**錯的推論**,別拿它當選 scope 的理由。

細節見 [04_AI讀不到怎麼查.md](04_AI讀不到怎麼查.md)。

### 分享 ≠ 搬家（最常見的誤解）

部門表分享給聊天室之後：

```
✅ 讀寫資料仍然走「部門」的路徑
❌ 不是改走「聊天室」的路徑
```

**判斷方式**：看那張表回傳的資料裡,`chatroom_id` / `department_id` / `company_id` 哪個有值 —— 那個就是它的擁有 scope。**不是看「我現在在哪個聊天室」。**

### 怎麼選:只有三個理由該讓你選 department

| 選 department 的正當理由 | 為什麼 |
| :--- | :--- |
| **這批資料要給多個聊天室用** | 分享不搬資料,一份主檔多室共用 |
| **需要「同一張表,不同聊天室看不同列」** | 只有這層有這個機制 |
| **未來要擴充分公司／區域／團隊** | 一個分公司一個 department |

**沒有上面任何一條的話,放 chatroom 其實更簡單**：表格模組直接可用、AI 只要開一道關、不用 grant、不用勾選系統。

| Scope | 該用的時機 | 代價 |
| :--- | :--- | :--- |
| **chatroom** | 這批資料**永遠**只屬於這一個群組 | 不能按聊天室切列;要共用時只能重建（scope 改不了） |
| **department** | 上面三個理由任一成立 | 表格模組打不開,前端得自己刻;AI 要開三道關且缺 UI |
| **company** | 全公司唯一的基準資料（幣別、稅率） | 沒有房間隔離,權限只能逐一給 |

> 💡 **注意「command 原子性」不是選 department 的理由。** 它要求的是「整組表同一層」,而 chatroom 同樣滿足 —— 只要整組都在 chatroom。

### ⚠️ 但 scope 改不了,所以要看未來

因為 [改不了](#-但跟-windows-資料夾不一樣建了不能搬),決策要用「未來 12 個月」的眼光,不是現在。

**驗屋案的例子**：需求寫「第一版綁定單一聊天室,但資料結構預留分公司、區域、團隊與跨聊天室範圍」。

- 只看第一版 → chatroom 就夠,而且更簡單
- 但「預留跨聊天室」意味著遲早要共用,而那時候改不了 → **選 department**

**理由是「scope 改不了 + 未來要共用」,不是「AI 需要」。**

### 一個順帶的坑:URL 有四種形狀

官方文件兩處看起來矛盾（一處說 company 路徑沒有 `company_id`、一處說有）。**兩邊都對,它們在講不同的路由族：**

| 路由族 | company 長相 |
| :--- | :--- |
| 一般（表／列／欄位／規則／IaC…） | **沒有** `company_id` |
| **commands** | **有** `company_id` |
| 附件上傳、公開讀取 token | 三個 scope **都沒有** scope id |
| 「誰分享給我」的發現端點 | **完全沒有** scope 前綴 |

💡 **這是值得回饋給後端團隊的文件缺口** —— 照 `concepts/scopes` 那頁組 command 的 URL 會組錯。

## 決定三：tag 怎麼切

Tag 看起來只是「整理表的資料夾」,實際上它同時是三件事的邊界：

```
            ┌──────────────┐
            │     Tag      │
            └──────┬───────┘
      ┌────────────┼────────────┐
      ▼            ▼            ▼
  表的分組    command 邊界   AI 載入單位
```

| 這條邊界 | 意思 |
| :--- | :--- |
| 表的分組 | 哪些表屬於同一個系統 |
| **command 邊界** | 一支 command 只能碰同 tag 的表。碰到 tag 外的表 → 被拒絕 |
| **AI 載入單位** | 聊天室管理者是「按 tag」勾選要讓 AI 載入哪些部門系統 |

**所以 tag 切錯了會有兩種症狀**：command 寫不出來,或者 AI 的載入範圍不對。

實務上通常就是「一個業務系統 = 一個 tag = 一份 IaC 文件」（IaC 文件的 header 本來就帶 `system` 欄位）。

## 其他要知道的事

決定完三件事之後,以下是設計過程中會撞到的東西。**都只講方向,細節去官方文件。**

### 關聯欄位只能「由窄往寬」

```
       company（最寬）
          ▲
     department
          ▲
      chatroom（最窄）
```

聊天室的表可以關聯到部門或公司的表 ✅。反過來（部門 → 聊天室）、或平行（聊天室 A → 聊天室 B）都會被拒絕。

### 計算欄位是最常踩的一類坑

`link`、`rollup`、`lookup`、`formula` 的值 **從不落地**（讀取時才算）。所以 **很多地方不能用它們** —— 規則的條件、權限的列過濾、不可重複鍵…都只吃普通欄位。

設計卡住的時候,先檢查是不是想在這些地方用計算欄位。

### Rules：先知道有哪些,別背細節

| 你想表達的 | 用哪條 |
| :--- | :--- |
| 這個欄位必填（可以是「符合某條件時才必填」） | `require` |
| 這幾個欄位的組合不可重複 | `unique`（DB 層約束,擋得住併發） |
| 值域檢查（金額不可為負） | `check` |
| 兩個欄位的關係（結束不得早於開始） | `compare` |
| 狀態只能沿允許的路徑走 | `transition` |
| 一旦送出／過帳就不能再改 | `immutable_when` |
| 同一個人的時段不可重疊 | `no_overlap` |
| 另一張表必須／不得存在符合資料 | `exists` / `not_exists` |
| 超過某金額要簽核 | `require_approval` |
| 同一張部門表,不同聊天室看不同列 | `channel` |
| 不論從哪個入口寫都要符合的底線 | `invariant` |

> ⚠️ 大多數規則可以帶條件,但 `immutable_when` 用的是「寫入**之前**」的資料判斷 —— 因為如果用寫入後的資料判斷,呼叫者只要在同一筆請求裡「解鎖 + 修改」,鎖就永遠不生效。

### 排班／預約:平台有內建的,不要自己刻

```
班表表（每週樣板 + 特定日期例外）
    │  每日排程掃描
    ▼
時段表（每個人 × 日期 × 起始時間 一列）
    │
    ├─ 不可重複規則  ← 讓併發認領不會撞車
    └─ 不可重疊規則  ← 防衝堂
```

**你只宣告一次「每週怎麼排班」,每日掃描自動維持未來一段時間的具體時段。** 不用手動插入時段,也不用自己寫排程程式。

三個方向性警告：

- **掃描只會新增,從不修改或刪除。** 改了班表不會動到已產生的未來時段 —— 過時的要人工取消
- **已取消的時段不會被重新掃描復活。** 取消掉就是取消掉了
- **時段表不能掛簽核規則。** 否則每日掃描都會死在簽核關卡

> 完整參數與地雷 → [triggers/materialize-slots](https://docs.customtable.teamsync.com.tw/zh-TW/concepts/triggers/materialize-slots)
> 從零做完一套 → [use-cases/booking](https://docs.customtable.teamsync.com.tw/zh-TW/use-cases/booking)

### 簽核只掛主檔

⚠️ **一支 command 只能觸及「一張」有簽核規則的表**,超過一張直接被拒絕。

**所以報價單 + 明細這種結構,簽核規則只掛主檔,不要也掛明細。** 否則「建立報價單」一執行就爆。

### 權限對「人」是兩層

```
① 能不能用這張表      能讀？能寫？能改？
② 能看到哪些列        同一張部門表，A 群組看 A 的料，B 群組看 B 的料
```

第二層只有部門表有意義。最反直覺的一點：**呼叫者永遠不指定自己代表哪個群組,伺服器自己算** —— 而且算出來的是「你所屬、且對這張表有授權的**每個**群組」的**聯集**。

這解釋了幾個常被當成 bug 的現象：

| 現象 | 其實是 |
| :--- | :--- |
| 資料筆數比預期多 | 那是聯集的計數 |
| 同時在兩個群組的人看到兩邊資料 | 設計如此 |
| 沒有任何合格群組 → 讀取回空的,不是錯誤 | 讀取不要求你宣告範圍 |
| 沒有任何合格群組 → 寫入被拒 | 只有寫入需要宣告 |

> ⚠️ 舊的「指定我代表哪個群組」參數已經移除,**但送了不會報錯** —— 請求照樣成功,而你指名的群組根本不被採用。還在用的用戶端要移除它,不會有任何訊息提醒你。

## 反模式清單

| ❌ 反模式 | 為什麼錯 | ✅ 改成 |
| :--- | :--- | :--- |
| 「主檔放部門、交易資料放聊天室」 | 跨兩層的原子寫入會被拒絕 | 先圈出「要一起寫的那一組」,整組同一層 |
| 「先建聊天室的表,以後要共用再搬上去」 | **scope 改不了**,只能匯出重建 + 自己搬資料 | 一開始就評估會不會共用;有疑慮先放 department |
| 「部門表分享給聊天室後,改用聊天室路徑讀」 | 分享不搬家 | 看表回傳的欄位判斷擁有 scope |
| 「company 表當 department 用（反正全公司都看得到）」 | 沒有房間隔離、AI 載入機制 | 需要按群組切範圍就必須 department |
| 「AI 讀不到,那應該是權限沒給」 | 權限之外還有兩層開關 | 照 [04](04_AI讀不到怎麼查.md) 的順序排查 |
| 「排班自己刻一套」 | 平台有內建的三件套 | 先看 use-cases/booking |

## 動手前的自我檢查

**決定一**
- [ ] 有哪些動作會同時改到兩張以上的表、且不能只成功一半?
- [ ] 那些表我圈成同一組了嗎?

**決定二**
- [ ] 這一組放哪一層?為什麼不是另外兩層?
- [ ] 未來 12 個月內,這批資料有可能要分享給第二個群組嗎?（會 → 不要放 chatroom）
- [ ] 需要「不同群組看不同列」嗎?（要 → 必須 department）
- [ ] 我選 department 的理由,是那三個正當理由之一嗎?（「要給 AI 用」**不是**正當理由）
- [ ] 我確定 **scope 之後改不了** 這件事嗎?

**決定三**
- [ ] tag 怎麼切?圈出來那一組是不是都在同一個 tag 底下?

**其他**
- [ ] 有沒有關聯欄位是由寬往窄、或平行的?（會被拒絕）
- [ ] 有沒有在規則條件、列過濾、不可重複鍵裡用到計算欄位?（不能用）
- [ ] 簽核規則有沒有掛在超過一張、會被同一支 command 碰到的表上?
- [ ] 要做排班的話,我是不是在重刻平台已經有的東西?
