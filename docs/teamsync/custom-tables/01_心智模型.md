# Custom Tables 心智模型

> **對象**：PM／RD
> **目的**：用「你平常怎麼寫後端」來理解 Custom Tables,而不是背它的名詞
> **對應版本**：teamsync-backend `5.7.1`（`328f7817`）
> **撰寫日期**：2026-08-04

---

## 1. 它不是一個功能,是一個後端替代品

平常做一個新模組,流程是這樣:

```
寫 SQLAlchemy model → 寫 alembic migration → 寫 CRUD → 寫權限檢查
→ 寫 API → 寫篩選排序分頁 → 寫附件上傳 → 寫稽核 log → 寫匯入匯出
```

Custom Tables 的主張是:**這些你其實都不用寫**。

你只「宣告」要什麼表、什麼欄位、什麼規則,引擎自己長出上面全部。所以它該被理解成 **後端替代品**,不是「TeamSync 多了一個表格功能」。

省下的是後端。**前端還是要自己刻**（或用現成的表單 UI）。

## 2. 名詞對照表 —— 這裡沒有新概念

覺得複雜是因為一次看到全部。一一對照就會發現,每一項你都已經會了:

| 你平常寫 code 做的事 | Custom Tables 的名字 |
| :--- | :--- |
| 建 table、加欄位 | **tables** / **columns** |
| Foreign key、JOIN 撈關聯資料 | **link** / **lookup** / **rollup** |
| 算欄位（小計 = 單價 × 數量） | **formula** |
| `if not xxx: raise ValueError` 那些檢查 | **rules** |
| 「同一個醫師不能同時段兩筆預約」 | rules 的 **no_overlap** |
| 「訂單號不可重複」 | rules 的 **unique** |
| 「狀態只能 待審 → 已審 → 結案」 | rules 的 **transition** |
| 「這個欄位送出後就不能改」 | rules 的 **immutable_when** |
| 「超過 10 萬要主管簽核」 | rules 的 **require_approval** |
| Celery 定時任務 | **triggers**（`on: schedule`） |
| Signal / `after_insert` hook | **triggers**（created/updated/deleted/restored） |
| Webhook 通知外部系統 | **callback** |
| 一支 API 裡包一個 transaction 寫三張表 | **commands** |
| `WHERE user_id = ...` 那些權限過濾 | **ACL** / **grant** / **SCP** |
| 軟刪除 + 還原 + 修改紀錄 | **history** / **trash** |
| Excel 匯入 | **import** |
| 檔案上傳到 S3 | **attachment** / **blobs** |
| 存好的搜尋條件 | **views** |
| 讓 AI 能查你的資料 | **agent toolkit** / **insight systems** |
| 把 schema 進版控、複製到別的環境 | **IaC** → 見 [02_IaC.md](02_IaC.md) |

**從「寫 Python」變成「填 JSON」,這就是全部的變化。**

## 3. 欄位型別（17 種）

來源：`src/schemas/enums.py:110` `class ColumnType`

| 分類 | 型別 | 說明 |
| :--- | :--- | :--- |
| 基本純量 | `string` `text` `integer` `float` `boolean` `date` `datetime` | 值存在 `record.data` JSON 內 |
| 選項 | `select` `multi_select` | 寫入會對照欄位的 `options` 驗證 |
| 關聯 | `link` | Airtable 風格。值存在 `custom_table_record_links`,**不在** `record.data` |
| 計算（唯讀） | `rollup` `lookup` `formula` | 讀取時算出來,值從不落地 |
| 檔案 | `attachment` | 值是 S3Object id 列表,讀取時解析成 metadata |
| 任意結構 | `json` | 只支援 `is_null`/`is_not_null` 與純量 `eq/neq/in`,不能參與 rollup/formula/unique |
| 身分 | `user` `social_client` | 存單一 raw id 字串。**只能做等值比較**（`eq/neq/in/is_null`）,不能排序或 contains |

四種「計算欄位」（`link`/`rollup`/`lookup`/`formula`）在程式裡是一組：`COMPUTED_COLUMN_TYPES_PD`（`src/schemas/custom_tables.py:230`）。它們是唯讀的,而且不能出現在很多地方（`when` predicate、row policy、unique key），這是最常踩的一類坑。

## 4. 三種「殼」,共用同一份資料

宣告完之後,同一批資料可以被三種殼包起來。**不是三份資料,是一份資料三個入口** —— 所以不存在同步問題。

```
                    ┌──────────────────┐
                    │   同一份資料      │
                    │ （Custom Tables） │
                    └────┬────┬────┬────┘
              ┌──────────┘    │    └──────────┐
              ▼               ▼               ▼
     ┌────────────────┐ ┌──────────┐ ┌────────────────┐
     │  ① 表格模組     │ │ ② AI     │ │ ③ 你自己刻的    │
     │    （通用）     │ │  聊天室   │ │    模組頁面     │
     └────────────────┘ └──────────┘ └────────────────┘
      使用者自己建表      用嘴問        客戶要的專屬流程
      像內建 Airtable                  by case 自己做
```

從自己刻的頁面改一筆資料,使用者從表格模組看也是改過的,AI 問也是新的。**只有一份。**

| 殼 | 誰用 | 誰做 | 位置 |
| :--- | :--- | :--- | :--- |
| **① 表格模組** | 一般使用者自己建表、填資料、篩選、匯入匯出、看統計 | 已經有了,通用 | `app/chat/components/forms/`（入口 `app/chat/interfaces/FormsInterface.tsx`） |
| **② AI 聊天室** | 用自然語言問「這週還有幾個空班」 | 已經有了,開 job 就行 | agent toolkit → 見 [05_AI存取的四層.md](05_AI存取的四層.md) |
| **③ 自己刻的模組頁面** | 特定客戶的專屬流程（案件中心、班表、報價單） | **by case 自己刻** | `app/modules/<name>/`,先例：`app/modules/spc/hooks/useTeamSyncSpecTable.js` |

### 這三種殼怎麼選

| 你的需求 | 用哪個殼 |
| :--- | :--- |
| 使用者要自己建表、自己決定欄位（報帳單、打卡表） | ① 表格模組,不用寫程式 |
| 客戶要特定 IA（module tabs + Detail Panel + 班表 + Dashboard） | ③ 自己刻。① 是「聊天室表單」形態,套不上來 |
| 想讓 AI 回答資料問題 | ② 加開,跟 ① ③ 不衝突 |

### 資料層都是同一批 REST API

```
/private/module/custom_tables/chatroom/{chatroom_id}/tables/{table_id}/records
/private/module/custom_tables/department/{department_id}/tables/{table_id}/records
/private/module/custom_tables/company/tables/{table_id}/records
```

前端 service 層**已經全部產生好了**（`services/teamSync/moduleCustomTables*.js`），三種 scope 全套,不用自己寫 HTTP。

> ⚠️ 但殼 ① 目前只認**聊天室自己的表**,打不開部門表；殼 ② 讀部門表的 job 開關前端也還沒有。只有殼 ③ 三種 scope 都能用。詳見 [05_AI存取的四層.md](05_AI存取的四層.md)。

### AI 這個殼有一個容易踩的坑

工具分兩層：

| 主 agent 可直接呼叫 | 只有「分析子 agent」能跑 |
| :--- | :--- |
| `custom_tables_find_records`、寫入工具、指令工具、blob 工具、`custom_tables_cheat_sheet` | `query_records`、`aggregate_records`、`profile_column`、`correlation`、`join_aggregate`、`traverse_links` |

主 agent **叫不到右欄**,必須把問題委派給 `custom_tables_analyze`。

其他要知道的：

- 分析子 agent 的 prompt 開頭注入 `CURRENT DATE (UTC)`。**錨點是 UTC** —— UTC+8 使用者早上 07:00 問「今天」,解出來是前一個日曆日
- 支援滾動時間窗 `within_last` / `within_next` / `older_than`（正整數天數,或 `{"amount":N,"unit":"days"|"hours"}`）
- 計算欄位可過濾與排序,但**上限 50,000 筆存活資料**

## 5. Commands —— 業務邏輯寫在這裡

### 白話：command 就是 stored procedure

**Command ≈ SQL Server 的預存程序。** 一段存在伺服器上、具名、可帶參數的程式,在**同一個 transaction** 內寫多張表,以**呼叫者本人的權限**執行（沒有 definer rights、沒有 service account）。

所以業務邏輯 **是要寫在 command 裡的**,不是丟給前端。

### 為什麼需要它:看一個具體例子

「下訂單 = 建主檔 + 建 3 筆明細 + 扣庫存」。

**沒有 command,前端要這樣做：**

```
POST 訂單主檔        → 拿到 order_id
POST 明細 1
POST 明細 2
POST 明細 3          ← 這裡失敗了
PATCH 扣庫存
```

第 4 步失敗,前端得自己回頭把主檔和前兩筆明細刪掉（自己發明補償邏輯）。而且使用者網路卡了重按一次,你會得到**兩張訂單**。

**有 command：**

```
POST /commands/{建立訂單}/execute
     inputs + idempotency_key
```

**一次呼叫。要嘛全部成功,要嘛什麼都沒發生。** 重按也只有一張訂單。

> 模組裡沒有別的東西提供跨表原子性。bulk operations 掛在單一表底下,所以「主檔一列 + 明細數列」本質上是兩個獨立 transaction。

### 為什麼不該把業務邏輯放前端

不是「不好」,是**會少五樣東西**：

| 少了什麼 | 後果 |
| :--- | :--- |
| 交易保證 | 中途失敗要自己寫補償邏輯 |
| 重送保護（idempotency） | 網路重試就重複寫一筆 |
| 稽核紀錄 | 出事查不到誰在何時做了什麼 |
| **AI 也能用同一份邏輯** | command 存好就自動變成 agent 工具；前端邏輯 AI 用不到 |
| 單一真相 | 前端／REST／AI 三個入口各實作一份 → 必然漂移 |

**前端該做的是「編排 + UI」**：讓使用者填表、選人、確認,然後呼叫一支 command。

### 兩個版本

| 版本 | 能力 | 何時用 |
| :--- | :--- | :--- |
| v1 | 扁平寫入 DSL：一串有序 steps,無讀取、無 join、無 outputs | 純寫入扇出（主檔 + 明細、狀態變更 + 稽核列） |
| v2 | 小型關聯式程式,讀取是一級公民,有 `outputs` | 需要先查資料、需要 join 或彙總 |

### v2 的六種 step

| `kind` | 用途 | 綁定 |
| :--- | :--- | :--- |
| `select` | 從表、既有 relation 或字面值讀出一個有界 relation | `$rel.<name>` |
| `let` | 由運算式算出一個具名值 | `$var.<name>` |
| `assert` | 條件為 false 時讓整次執行失敗（`422 assertion_failed`） | 無 |
| `insert` / `update` / `delete` | 寫入 | `$rel.<name>`（其 `returning` 對映） |

上限：**最多 40 個 steps**,其中 `insert`／`update`／`delete` 合計最多 **20 個**。

### ✅ 條件與迴圈都有 —— 只是不長成 Python 的樣子

這點很容易誤判。它 **不是** 「只能直線寫入」：

| 你想寫的 | command 裡怎麼寫 |
| :--- | :--- |
| `x = 條件 ? a : b` | `$case` |
| `if (條件) { 做這步 }` | 那個 step 加 `when`。條件不成立就標記 `skipped`,綁空 relation 不執行 |
| `for (item of list) { insert }` | 寫入 step 的 `for_each`。v2 起是**完整運算式**（不限 `$input.<array>`），元素用 `$item.<field>` |
| `SELECT … JOIN …` | `select` 的 `joins`（最多 4 個，`inner`／`left`／`right`，或 link join） |
| `GROUP BY … HAVING … ORDER BY …` | `select` 全部支援（`group_by` ≤20、`order_by` ≤20、`limit` 1–1000） |
| 「挑出案件最少的那個人」 | `select` + `group_by` + `order_by count asc` + `limit 1` → `$first` |
| 斷言「剛好一筆匹配」 | `$single`（不是恰好一列時回 `400 cardinality_failed`） |

**實例:「固定業務優先,沒有才找案件最少的人」** —— 這寫得出來,不用 Python：

```
① select 建案 → 取固定業務
② select 業務 join 案件 → group_by 業務 → order_by 案件數 asc → limit 1
③ let assignee = $case(① 有值 → 用 ①, else → 用 ②)
④ update 案件 set 負責業務 = $var.assignee
```

運算子詞彙相當完整：算術比較（`$add` `$sub` `$mul` `$div` `$eq` `$gt` `$between` `$in` `$and` `$or` `$not` `$is_null`…）、字串（`$concat` `$len` `$lower` `$upper`）、日期（`$today` `$year` `$month` `$datediff`）、JSON（`$json_get` `$json_parse`…），以及 **`$case`**。

六個 relation helper：`$exists`、`$count_rows`、`$aggregate`（`count`/`count_distinct`/`sum`/`avg`/`min`/`max`）、`$collect`、`$first`、`$single`。

> ⚠️ `$first` / `$collect` 需要**有序**的 relation。寫入 step 的 `returning` relation **不是有序**,對它用這兩個是 authoring 錯誤 —— 需要有序語意就在 `select` 上宣告 `order_by`。

### ❌ 真正沒有的東西

| 沒有 | 影響 |
| :--- | :--- |
| **while / 遞迴 / 動態步數** | 步驟清單是靜態的。「一直做到某條件成立」表達不出來 |
| **呼叫外部服務** | OCR、第三方 API、寄信 —— 要用 `callback` 或寫 Python |
| **regex / 相似度函數** | 字串只有 `concat`／`len`／`lower`／`upper`。模糊比對（疑似重複資料）做不到 |
| **超過 40 步 / 20 個寫入** | 大型批次要拆多支 command 或改用 bulk operations |

### 所以什麼該放 command、什麼不該

| ✅ 適合 command | ❌ 必須寫 Python |
| :--- | :--- |
| 訂貨 = 主檔 + 明細 + 扣庫存 | 名片辨識 OCR |
| 認領時段 = 檢查 + 佔位 + 更新（原子 + idempotent） | 疑似重複資料的相似度比對 |
| 報價改版 = 複製上一版 + 版號 +1 | 需要 while 或遞迴的演算法 |
| **「固定業務優先,未命中才輪班」** —— `select` 取固定業務、`select`+`group_by`+`order_by` 取最少案件者、`$case` 二選一 | 呼叫外部報表引擎產 PDF |

### 兩條執行通道

| 通道 | 用途 |
| :--- | :--- |
| `POST .../commands/{id}/execute` | 交易式寫入。保留 idempotency key、留執行稽核紀錄、命中 `require_approval` 時整份計畫暫存並回 `409` |
| `POST .../commands/{id}/query` | 只給 `mode:"query"` 的唯讀指令。不上鎖、cursor 分頁、無 replay key、不留紀錄 |

走錯通道回 `409`,不會默默執行。

另有 `/agent/commands/…` 通道,由服務 token 驗證,scope 與 acting room 從注入的 header 推導。

### 建置門檻高於呼叫（刻意設計）

建立 command 需要管理權,並指定 tag；**執行** 只需要對那些表的讀取權 + 各步驟本身所需權限。所以你可以把一個範圍明確、有稽核紀錄的寫入動作,交給沒能力自行建置它的人。

### command 自動變成 AI 工具

`agent_enabled` **預設 `true`**。存檔後這支 command 就出現在聊天室 agent 的工具清單裡,`description`（上限 1024 字元）就是 tool description。

**這是「把業務邏輯變成 AI 能力」的正式路徑** —— 不是 MCP。Custom Tables 沒有 MCP server（`src/routers/private/user/mcp.py` 是 Google OAuth 憑證管理,方向相反）。

## 6. 唯一的 JOIN 路徑

**記錄查詢 API 沒有 JOIN。**

`mode:"query"` 的 command 是模組裡唯一的伺服器端 join 與彙總讀取路徑。它刻意做得很便宜：不加鎖、不寫稽核、不留 idempotency key、session 最後直接 rollback。

Authoring 要求：`version: 2`、**零個**寫入 step、無 `callbacks`、無生命週期 `triggers`。

## 7. 代價 —— 講完好處要講這個

| 代價 | 實際影響 |
| :--- | :--- |
| 不能自由寫 SQL | 記錄查詢 API 無 JOIN,要 join 只能寫 query-mode command |
| Command 沒有 while / 遞迴 | 步驟清單靜態（≤40 步、≤20 寫入）。條件與迴圈有（`$case`／`when`／`for_each`），但「做到條件成立為止」做不到 |
| 不能呼叫外部服務、沒有 regex | OCR、模糊比對、產 PDF 都得寫 Python 或走 callback |
| 有硬上限 | 計算欄位過濾/排序上限 5 萬筆存活資料；`materialize_slots` 一次最多插 1000 列 |
| 欄位真名是 `col_<hex>` | 顯示名稱只是別名（為了支援改名）。filter / sort 要用內部鍵,接 API 最常踩這個 |
| 學習曲線前置 | 得先搞懂 **scope**、**column identity**、**權限模型** 三件事,不然每次呼叫都會踩坑 |

---

## 8. 判斷要不要用它

> 你的模組是不是「一堆表 + 一堆欄位 + 一堆規則 + 一堆權限」?

- **是** → 用它。後端能省 80~90%。
- **部分是**（大部分 CRUD + 少數演算法）→ 用它當資料層,演算法寫 Python。這是最常見的情況。
- **不是**（重運算、重外部整合、要自己調 SQL）→ 不要硬套。
