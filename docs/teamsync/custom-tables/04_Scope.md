# Scope:chatroom / department / company 到底差在哪

> **對象**：要決定「我的表放哪一層」的 RD／PM
> **目的**：講清楚三層的差別、為什麼選錯改不回來、以及為什麼答案通常是 department
> **對應版本**：teamsync-backend `5.7.1`（`328f7817`）／teamsync-frontend（`cbd123f2`）
> **撰寫日期**：2026-08-04
>
> 📖 **精確的 URL、auth matrix、錯誤格式去官方文件查**：<https://docs.customtable.teamsync.com.tw/zh-TW/concepts/scopes>

---

## 一句話總結

**Scope 決定三件事:表由誰擁有、URL 掛在哪、請求先過哪一層驗證。**

而且它 **建表時就決定,之後改不了** —— 這是整個 Custom Tables 裡最不可逆的一個決定。

---

## 1. 白話:三層就是「這張表是誰的」

```
company     ← 全公司共用的基準資料（幣別、稅率、產品分類）
   │
department  ← 某個部門維護、但要分享給好幾個聊天室用
   │
chatroom    ← 只有這一個聊天室在用，別人不會碰
```

| | **chatroom** | **department** | **company** |
| :--- | :--- | :--- | :--- |
| 擁有者 | 一個聊天室 | 一個部門 | 整間公司 |
| 誰能建表 | 聊天室成員／有存取權的人 | 有部門存取權的人 | 有公司存取權的人 |
| **AI 能不能讀**（用 tag 組成 Insight system） | ❌ | ✅ **只有這層** | ❌ |
| **能不能「同一張表,不同聊天室看不同列」**（SCP） | ❌ | ✅ **只有這層** | ❌ |

**中間那兩列是關鍵。** 這兩個能力只存在 department scope,而它們通常直接決定答案。

---

## 2. ⛔ Scope 改不了 —— 最重要的一節

更新表的 payload 只有 `name` 和 `description`。**沒有任何欄位可以改 scope。**

| 想做的事 | 可行嗎 |
| :--- | :--- |
| 把 chatroom 表改成 department 表 | ❌ 沒有這個操作 |
| 把 department 表搬到另一個部門 | ❌ 沒有這個操作 |
| 分享給別的聊天室／部門 | ✅ 用 grant,但**表不會搬家**（見第 3 節） |

**唯一的補救很貴**：把 schema 匯出成 IaC 文件 → 換掛載點重新套用 → **資料自己搬** → 重接所有關聯欄位 → 重建權限、規則、觸發器。

而且如果系統裡有跨表的觸發器（例如班表產生時段），匯出時遇到懸空引用會直接失敗而不是硬輸出 —— 搬起來更麻煩。

> **所以選 scope 要在建表前想清楚。這是這份文件存在的主要理由。**

---

## 3. 分享 ≠ 搬家（最常見的誤解）

> **分享只增加存取權,不會搬動或複製資料表。**

部門表分享給聊天室之後：

```
✅ 讀寫資料仍然走「部門」的路徑
❌ 不是改走「聊天室」的路徑
```

**判斷方式**：看那張表回傳的 `chatroom_id` / `department_id` / `company_id`,誰有值就是它的擁有 scope。**不是從「我現在在哪個聊天室」推。**

分享有兩個方向,而端點永遠掛在「表的擁有 scope」那一側：

| 目的 | 端點掛在 |
| :--- | :--- |
| 讓一個**部門**存取**聊天室**的表 | 聊天室那側 |
| 讓一個**聊天室**存取**部門**的表 | 部門那側 |

另外有兩個**完全不帶 scope 前綴**的端點,用來發現「有誰分享給我」—— 因為呼叫者本來就不可能知道是哪個部門或哪個房間分享的。

---

## 4. URL 有四種形狀,不是三種

這裡官方文件看起來自相矛盾：

- `concepts/scopes` 說 company 的路徑「本來就沒有 `company_id`」
- `concepts/commands` 說 company 掛載點「同樣帶有明確的 `{company_id}`」

**兩邊都對 —— 它們在講不同的路由族。** 實際掛載有四種形狀：

| 路由族 | company 長相 |
| :--- | :--- |
| 一般（表／列／欄位／規則／檢視／IaC…） | **沒有** `company_id` |
| **commands** | **有** `company_id` |
| 附件上傳、公開讀取 token | 三個 scope **都沒有** scope id |
| 「誰分享給我」的發現端點 | **完全沒有** scope 前綴 |

> `src/routers/private/modules/custom_tables/server.py` 的註解原文：
> *"Commands carry an explicit scope id in every mount, including company scope."*

**不帶 scope id 不代表繞過 scope。** 伺服器會從 table id 找回擁有範圍並重新驗證你。

💡 **這是值得回饋給後端團隊的一個文件缺口**：照 `concepts/scopes` 組 command 的 URL 會組錯。

---

## 5. 為什麼答案通常是 department

| 你需要的 | department 給你什麼 |
| :--- | :--- |
| 跨聊天室共用 | grant 分享,不搬資料 |
| **command 原子性** | 所有表同 scope,可放同一個 tag（見 [03](03_關鍵約束.md) 第 2 節） |
| **AI 能讀** | 只有這層能用 tag 組成 Insight system |
| **逐房間切資料範圍** | 只有這層的 SCP 有意義 |
| 未來擴充分公司／區域 | 一個分公司一個 department |

反過來看另外兩層什麼時候才真的該用：

| Scope | 該用的時機 | 為什麼通常不該用 |
| :--- | :--- | :--- |
| **chatroom** | 這批資料**永遠**只屬於這一個協作室,不分享,也不需要 AI 查 | 不能組 Insight system、不能被 SCP 切範圍 |
| **company** | 全公司唯一的基準資料 | 沒有房間隔離、沒有 tag 載入機制,權限只能逐一給 |

---

## 6. 權限是三層,不要混著看

```
① 進 scope 的門    「你能不能碰這個部門／聊天室／公司」
        ↓
② ACL / grant      「你能不能用這張表、能讀能寫到什麼程度」
        ↓
③ SCP（channel）   「以你被授權的那些房間，你可以碰哪些列」
```

第三層只有 department scope 有意義（部門表被多個聊天室共用時）。

### SCP 最反直覺的一點:**呼叫者永遠不指定房間**

伺服器自己算。表管理者豁免;其他人拿到的是「你所屬、且對這張表有授權的**每個**聊天室」的範圍**聯集**。

這解釋了幾個常被當成 bug 的現象：

| 現象 | 其實是 |
| :--- | :--- |
| 資料筆數比預期多 | 那是聯集的計數 |
| 同時在兩個房間的人看到兩邊的資料 | 設計如此 |
| 沒有任何合格房間 → 讀取回空的,不是錯誤 | 讀取不要求你宣告範圍 |
| 沒有任何合格房間 → 寫入被拒 | 只有寫入需要宣告 |

> ⚠️ **舊的 `acting_chatroom_id` 參數已經移除,但送了不會報錯。** 請求照樣成功,而你指名的房間根本不被採用 —— 你靜默地拿到了聯集。還在用的用戶端要移除它,不會有任何訊息提醒你。

## 7. 反模式清單

| ❌ 反模式 | 為什麼錯 | ✅ 改成 |
| :--- | :--- | :--- |
| 「主檔放 department、交易資料放 chatroom」 | 只要有跨兩層的原子寫入就會被拒絕 | 要一起原子寫的表全部同 scope 同 tag |
| 「先建 chatroom 表,以後要共用再搬上去」 | **scope 改不了**,只能匯出重建 + 自己搬資料 | 一開始就評估會不會共用;有疑慮先放 department |
| 「部門表分享給聊天室後,改用聊天室路徑讀」 | 分享不搬家 | 從表回傳的欄位判斷擁有 scope |
| 「送 `acting_chatroom_id` 指定代表哪個房間」 | 參數已移除,靜默失效 | 移除它,理解伺服器用的是聯集 |
| 「company 表當 department 用（反正全公司都看得到）」 | 沒有房間隔離、沒有 tag 載入機制 | 需要逐房間切範圍就必須 department |
| 「URL 尾段一樣,所以權限一樣」 | 新增欄位、診斷、解析連結這幾組操作在三個 scope 已知會分歧 | 查該端點的 scope/auth matrix |

## 8. 建表前的自我檢查

- [ ] 這張表會不會跟另一張表被**同一個動作原子寫入**?那些表全部同 scope 同 tag 了嗎?
- [ ] 未來 12 個月內,這批資料有可能要分享給第二個聊天室嗎?（會 → 不要放 chatroom）
- [ ] 需要讓 AI 查這批資料嗎?（要 → 必須 department）
- [ ] 需要「同一張表,不同聊天室看不同列」嗎?（要 → 必須 department）
- [ ] 有沒有 link 是向下或平行的?（會被拒絕）
- [ ] 我確定 **scope 之後改不了** 這件事嗎?
