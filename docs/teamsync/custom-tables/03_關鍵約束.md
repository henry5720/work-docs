# 設計 schema 之前必須知道的硬約束

> **對象**：RD（要動手設計 schema 的人）
> **目的**：把散在二十幾頁官方文件裡、但一定會踩到的約束集中在一頁
> **對應版本**：teamsync-backend `5.7.1`（`328f7817`）／custom-tables-docs（`ed5bc4c`）
> **撰寫日期**：2026-08-04
> ⚠️ 這頁的每一條都附了 source。官方文件會更新,有疑慮時以 code 為準。

## 一句話總結

**三條約束決定你的表要放哪一層：LINK 只能向上、Command 綁死單一 tag、Tag 是 scope-local。**

這三條會互相牽動,推導出來的結論通常是「**該一起操作的表,必須同 scope 同 tag**」。

---

## 1. 三種 scope

> 📖 **這一節是摘要。scope 的完整說明（含「scope 建表後不能改」、四種 URL 形狀、反模式清單）在 [04_Scope.md](04_Scope.md)。**

| Scope | 掛載前綴 | 適合的資料 |
| :--- | :--- | :--- |
| 聊天室 | `/private/module/custom_tables/chatroom/{chatroom_id}` | 只屬於一個協作室的工作資料 |
| 部門 | `/private/module/custom_tables/department/{department_id}` | 由部門維護、可分享給多個聊天室的系統資料 |
| 公司 | `/private/module/custom_tables/company` | 全公司共用（路徑本來就沒有 `company_id`） |

**分享只增加存取權,不會搬動或複製資料表。** 部門表分享給聊天室後,資料列 API **仍然走 `department/{department_id}`**,不是改走 `chatroom/{chatroom_id}`。這是接 API 最常搞錯的一件事。

### 權限是兩層,不要混在一起看

```
ACL / grant ：能不能使用這張表      → can_read / can_insert / can_edit
SCP         ：以呼叫者被授權的那些房間,可碰哪些列
```

驗證會先確認使用者能進入該擁有 scope,再合併「表管理者 + 使用者 + 部門 + 聊天室 + 預設 grant」算出有效的 `can_read` / `can_insert` / `can_edit`、列過濾與隱藏欄位。

**呼叫者永遠不指定房間** —— 伺服器逐表解析 channel floor：表管理者豁免；其他人拿到的是「所屬、存活、且對該表持有 internal grant 的每個聊天室」的 `scope_values` **聯集**。

> 這也是為什麼資料表清單／詳情頁的 `record_count` 就是這個聯集計數,以及為什麼多房間成員在詳情頁拿到 `200` 而不是過去的 `400`。

### 兩組例外路徑（無 scope ID）

- 附件 multipart：`/{scopeName}/tables/{table_id}/blobs/...`
- 背景遷移狀態：`/{scopeName}/migrations/{migration_id}/status`

仍要選對 `chatroom` / `department` / `company` 掛載,伺服器會從表或全域唯一的 migration ID 找回擁有範圍並重新驗證 —— 不是繞過 scope。

### ⚠️ `acting_chatroom_id` 已死,但不會報錯

2026-07-29 起,五個 `*Scoped` dependency 變體全部刪除,`?acting_chatroom_id` 從全部 57 個 custom-table 操作移除。

**危險在於它不會報錯**：FastAPI 丟棄未知 query parameter,所以請求照樣 `200`,而你指名的房間根本不被採用 —— 你靜默地拿到了「所屬、存活、且對該表持有 internal grant 的每個聊天室」的 `scope_values` **聯集**。

還在釘選房間的用戶端要把這個參數移除。**不會有任何訊息告訴你它失效了。**

沒有任何合格房間的呼叫者：讀取回 `200` 零列或 uniform `404`,只有寫入會被 `403 {"error": "scp_scope_undeclared"}` 拒絕。

## 2. 約束一：LINK 只能向上

> Source：`src/crud/custom_table_links.py:623` `validate_link_scope`

```
chatroom 表   ──link──▶  department 表 / company 表    ✅ 合法（向上）
department 表 ──link──▶  chatroom 表                   ❌ 拒絕（向下）
chatroom A 表 ──link──▶  chatroom B 表                 ❌ 拒絕（平行）
```

規則是：目標表必須與來源表 **完全同 scope**,或在**同一間公司內的更廣 scope**（company 最廣）。

downward / sibling cross-scope 一律 **fail closed**。跨公司也拒絕。

**設計含意**：主檔往上放（department／company），交易資料往下放（chatroom）—— 但下一條會推翻這個直覺。

## 3. 約束二：Command 綁死在「恰好一個 scope-local tag」

> Source：`src/crud/custom_table_commands/tags.py:1`、`src/schemas/custom_table_commands.py:1435`

```python
"""A command belongs to exactly one scope-local tag and may reference only
live tables assigned to that tag. REST authoring, IaC, direct execution,
approval release, and agent-tool loading all call this module so tag
membership cannot become a UI-only convention."""
```

`tag_id` 是 **必填**，錯誤碼三種：

| 錯誤碼 | 意思 |
| :--- | :--- |
| `tag_required` | 沒給 tag |
| `tag_not_found` | 這個 scope 裡找不到該 tag |
| **`tag_escaped`** | command 引用了 tag 外的表 |

**推論：command 無法跨 scope,也無法跨 tag。**

### 這條會直接推翻「主檔往上、交易往下」的直覺

假設你這樣切：

```
chatroom scope   : 案件 Cases
department scope : 班表 Shifts、時段 Slots、建案、業務、驗屋師
```

link 是合法的（向上）✅ —— 但只要有一個動作需要**同時原子寫兩張不同 scope 的表**,就爆掉：

```
認領 = update Slot（佔位） + update Case（填負責人），必須原子
      ↓
      command 只能綁一個 scope-local tag
      ↓
      Slot 在 department、Case 在 chatroom → tag_escaped ❌
```

沒有原子性,併發認領就會兩個人搶到同一個時段。

### ✅ 設計準則

> **凡是要被同一支 command 一起寫入的表,必須同 scope、同 tag。**

實務上這通常意味著：**整個系統的表都放 department scope**,再用 chatroom grant 分享出去。這樣同時滿足四件事：

| 需求 | department scope 給你什麼 |
| :--- | :--- |
| 跨聊天室共用 | chatroom grant,分享不搬資料 |
| command 原子性 | 所有表同 scope 同 tag |
| AI 能讀 | 部門 tag = Insight system,管理者可 opt-in |
| 未來分公司／區域 | 一個分公司一個 department |

## 4. 約束三：Tag 是三合一的邊界

Tag 不只是「整理表的資料夾」。它同時是三件事的邊界：

```
            ┌──────────────┐
            │     Tag      │
            └──────┬───────┘
      ┌────────────┼────────────┐
      ▼            ▼            ▼
  表的分組    command 邊界   AI 載入單位
             （tag_escaped）（Insight system）
```

**所以 tag 怎麼切,是整個設計裡最重要的一個決定。** 切錯了,command 寫不出來,或者 AI 載入範圍不對。

### Insight systems：tag 如何餵給 AI

```
GET / PUT  /private/chatrooms/setting/custom-table-tags/{chatroom_id}
```

`PUT` body 是 **完整 replace-set**,不是增量 patch：`{"tag_ids": [...]}`。送空陣列 = 關閉所有「有 tag」的 systems。

必須分清楚兩層：

```
ACL / grant  ：這個聊天室與使用者「可以」存取哪些資料   ← 安全邊界
Insight flip ：在已可存取集合中,聊天分析「要載入」哪些   ← 只是載入開關
```

| 事實 | 影響 |
| :--- | :--- |
| 只有 **department scope** 的表能靠 tag 組成 system | chatroom 自有表不在這個機制裡 |
| **untagged 的已授權部門表永遠載入** | 無法用「不給 tag」來隱藏,要能切換必須先加入某個 tag |
| 關閉 system **不是撤權** | 有 grant 的使用者照樣能用 API 讀到資料 |
| 伺服器只存 `tag_id`,每次重查 live grant + live tag | **bundle 會 drift**。前端不能把第一次拿到的清單釘死,要重新抓 |
| 前端 **只有 service 層,0 個 UI consumer**（`listCustomTableSystemsForChatroom`） | 目前只能用 API 開,沒有畫面 |

## 5. 欄位識別：`col_<hex>` 才是真名

顯示名稱只是別名（為了支援改名）。真正的鍵是內部 `col_<hex>`。

| 地方 | 用哪一種 |
| :--- | :--- |
| `filters` / `stored_filters` / `sort_by` | **內部鍵**（或 `id` / `created_at` / `updated_at`） |
| `computed_filters` 的 column | 顯示名稱或內部鍵都可 |
| saved view 的 `columns`（要顯示哪些欄位） | **顯示名稱** |
| rules 的 `when.column` | 兩種都可輸入,伺服器會存 rename-stable 的內部鍵 |
| trigger 回顯（`GET .../triggers`） | **混用**：`source` 的 ref 與 `link_map` 的**值**是顯示名稱；`target.slot_*`、`link_map` 的**鍵**、`defaults` 的鍵是目標表的內部鍵 |

⚠️ 最後那條的意思是：**設定 UI 不能假設回顯的 action 裡每個 ref 都是顯示名稱。**

## 6. Rules 的細節與地雷

### 十二種 rule 型別

> Source：`custom-tables-docs/content/zh-TW/concepts/rules/`

| 型別 | 白話 | 要點 |
| :--- | :--- | :--- |
| `require` | 條件式必填 | `when` 成立時,指定 stored scalar 不得為 `null` 或空字串 |
| `unique` | 不可重複的複合鍵 | **1~3 個欄位**。由資料庫層約束,能處理兩請求同時通過前端檢查的競態 |
| `check` | 單一 stored scalar 的值域檢查 | 數值界線、文字格式、有限集合 |
| `compare` | 同一列**兩個欄位**的關係 | 「開始日不得晚於結束日」、「實付不得高於核准額度」 |
| `transition` | 把欄位變成明確狀態機 | 限 `select`／`string`／`text`。**allowlist**：只有列在 `pairs` 的前後值組合能過 |
| `immutable_when` | 列的 **pre-image** 符合條件時凍結欄位 | 用 `prior_when`。這是唯一能表達「一旦 posted,數量就不能再改」的規則 |
| `no_overlap` | 同一範圍內區間不可重疊 | 防衝堂。半開區間 `[start, end)` |
| `exists` | 另一張可到達的表**至少有一列**符合 | 一跳式參照完整性：「出貨前必須有有效訂單」 |
| `not_exists` | 另一張表**不得存在**符合列 | 「仍有未結工單時不可結案」 |
| `require_approval` | 命中就進簽核,不直接生效 | live row 保持原狀,寫入存為 staged change |
| `channel` | SCP 的房間範圍安全 floor | 讓**同一張部門表**由多個 chatroom 共用,各自只看到自己的範圍。**呼叫者永遠不指定房間**,伺服器逐表解析 |
| `invariant` | principal-blind 的資料完整性 floor | 不論誰寫、從哪個入口寫（含 trigger action、callback、核准後 staged change 的套用）,post-image 都必須符合 policy |

> 需要條件式邏輯時：一般規則用 `when`；SCP 相關用 `channel` / `invariant` 的 `if` / `then` / `else` policy node。

### `when` 前置條件

- 陣列內最多 **5 個** predicate,全部以 **AND** 組合
- **只能引用 stored scalar 欄位** —— 不能用 `link`、`rollup`、`lookup`、`formula`
- operator：`eq` `neq` `gt` `gte` `lt` `lte` `contains` `in`（最多 100 項）`is_null` `is_not_null`
- `GET` 回來可能帶 `"when": null`,這是可安全原樣重送的正規化表示

### 五種規則不能用 `when`

| 規則 | 原因 |
| :--- | :--- |
| `unique` | 無條件的資料庫約束 |
| `transition` | 只看狀態前後值 |
| `channel` / `invariant` | 在各自的安全 floor 執行 |
| `immutable_when` | `when` 是以 **post-image** 判斷,鎖定條件會被那筆寫入自己打敗（同一 request 裡解鎖並修改）。它改用 `prior_when`,以 **pre-image** 判斷 |

帶了非空 `when` 會在設定階段 `400`。

### `no_overlap`（防衝堂）

```json
{
  "type": "no_overlap",
  "start_column": "開始時間",
  "end_column": "結束時間",
  "scope_columns": ["驗屋師"],
  "date_column": "驗屋日期",
  "when": [{"column": "狀態", "op": "neq", "value": "已取消"}]
}
```

| 約束 | 內容 |
| :--- | :--- |
| `start_column` / `end_column` | 必須是相同可排序類別；`end` 必須大於 `start` |
| `scope_columns` | **必須是 1~2 個 link 欄位** |
| `date_column` | 可省略；提供時可再按 date / datetime / 文字日期分組 |
| 區間語意 | **半開 `[start, end)`** —— 10:00 結束與 10:00 開始不算重疊 |
| 缺值 | 開始／結束／scope 缺值時該列**豁免**。若必須存在,另外加 `require` |
| 系統 `id` 欄位 | 三個欄位槽全部拒絕（2026-07-28 起） |

前端日曆可以先提示衝突,但**發布前用 `rules.preview` 檢視既有資料**,並以實際寫入回應為準。

### `require_approval`（簽核）

流程：

```
規則命中 → 寫入存為 staged change（live row 不變）→ 建 review process
→ reviewer approve／reject → approve 才套用
```

同步寫入命中規則時回 **`409`**，這是「已成功進入審批」不是「請重試」：

```json
{"detail": {"error": "approval_required", "process_id": "...", "rule_id": "...",
            "rule_label": "...", "staged_change_id": "..."}}
```

前端應導向 process／assignment 狀態,等決策後再刷新資料列。

**儲存規則時就會驗證 template 的 reviewer**：會擋掉未驗證／已到期的 reviewer,以及不存在／已軟刪／已停用／屬於其他公司的直接 user leaf。REST 是 `400`（detail 為單一字串）；**IaC 通道不是 `400`** —— executor 記成 apply error,其他行照常執行。

含**單一直接 user leaf** 的 template 是合法標的,不需要為一個人建 review group。

## 7. `materialize_slots`（班表 → 時段）的地雷集中區

這是官方 booking use-case 的核心機制,但地雷最多。

### 只能掛在 daily schedule 上

`on: "schedule"` 且 `schedule.type: "daily"`。`created`／`updated`／`deleted`／`restored`、`date_column_reached`、`interval` 全部在設定階段被拒絕。

它是**沒有觸發資料列的滾動 horizon 掃描**,不是逐列反應。

### 模型固定三個部分

```
班表 Shifts 表  ──[ daily trigger: materialize_slots ]──▶  時段 Slots 表
（每週樣板列 +                                              （provider × 日期 ×
  特定日期覆寫列）                                            起始時間 各一列）
                                                                  ▲
                                                    對 (slot_date, slot_start,
                                                     provider) 的 unique 規則
```

### 地雷清單

| # | 地雷 | 後果 |
| :--- | :--- | :--- |
| 1 | **目標表的 `unique` 規則實務上不是選配** | 沒有它,一次併發人工認領就讓整次掃描變成 failed run。有了它,併發衝突計入 `skipped_existing`,掃描能自我修復 |
| 2 | **收據 `window` 第二個元素不含** | `horizon_days: 30` 從 2026-07-25 起,收據是 `["2026-07-25","2026-08-24"]`,實際最後一天是 **2026-08-23**。對帳最常錯在這 |
| 3 | **不能指向掛了 `require_approval` 的表** | 設定寫入回 `409 approval_trigger_conflict`（否則每日 tick 都死在核准 backstop） |
| 4 | **Materializer 只 insert,從不 update／delete** | 縮短／刪除班表列、改 `slot_minutes` 或班別時間,**都不會動到已產生的未來時段**。過時時段必須人工取消 |
| 5 | **`slot_end` 不屬於自然鍵** | 手動改某個時段的**開始時間**後,下次掃描會在原本開始時間重建一列新的 |
| 6 | **存在性掃描沒有 soft-delete 過濾** | 已取消（soft-deleted）的時段仍算「存在」,重新掃描不會把它復活。**取消掉就是取消掉了** |
| 7 | **班表列的 provider link 帶多個目標** | 會產生**一列**同時帶全部目標的時段,而不是每人一列。**確保每列班表只對應一位 provider** |
| 8 | **每次 tick 插入上限 1000** | `truncated: true` 但 `ok: true` —— 這是**成功**不是錯誤,下次 tick 繼續填 |
| 9 | **每次掃描的班表列上限 1000** | 依 `created_at` 排序取 live 列,超出**靜默略過**。而且 `source.filter` 是在那個 1000 列查詢**之後**才套用 —— filter 搆不到建立時間排 1000 名之後的班表列 |
| 10 | **Trigger 鏈深度 3** | 每次時段插入會以 depth+1 觸發目標表自己的事件 trigger。一次 tick 最多可能產生 1000 個子 run |
| 11 | **覆寫列會完全取代該日樣板** | 若覆寫列的起訖 cell 無法解析而又沒標記關閉,該日產生**零個時段**,沒有回退也沒有錯誤 |
| 12 | **`defaults` 只能是字面值** | `$row` token 一律被拒（schedule trigger 沒有觸發列）。link 欄必須透過 `link_map` 設定 |
| 13 | **欄位刪除守衛只掃「完全同 scope」的兄弟表** | 若 materializer 向上寫入 department／company 的時段表,**目標側的欄位刪除不會被擋** |

### 其他要記的參數

| 參數 | 範圍 | 說明 |
| :--- | :--- | :--- |
| `horizon_days` | 1..92 | 從今天起連續填滿幾天 |
| `slot_minutes` | 5..1440 | 固定時段長度。**省略** = 每段班別產生剛好一個時段 |
| 切分 | — | 最後一段不完整的視窗**被丟棄**（09:00–10:20 切 30 分 → 只有 `09:00`、`09:30`） |
| 分段班表 | — | 同一 `(provider, 星期幾)` 寫多列會**累加**（上午一列、下午一列） |
| 權限 | — | schedule run 帶**系統**權限（actor 為 null）,時段列以該 trigger 的 `created_by` moderator 身分寫入 |

## 8. Commands 的審批交互

| 已執行計畫中受管控的表數 | 結果 |
| :--- | :--- |
| 零 | 正常 commit |
| **恰好一張** | Savepoint 回滾、計畫凍結成 `command_plan` staged change、執行轉 `staged`、回 `409 approval_required` |
| **超過一張** | `422 {"error":"multiple_approval_gated_tables","tables":[…]}` |

**設計含意**：報價單 + 明細這種結構,`require_approval` **只掛主檔（Quotes）,不要也掛明細（QuoteLines）**,否則 command 直接 `422`。

審批的預掃描是針對**真正執行過的計畫**（先在 savepoint 內跑一次,再拿具體 action 的真實前後影像比對規則），不是從定義層級推斷。

## 9. 上手前的檢查順序

1. 從表回應的 `chatroom_id` / `department_id` / `company_id` 判斷**擁有 scope**
2. 選用該 scope 的掛載與 endpoint 參考卡片（**不要從 URL 推論角色** —— 相同 endpoint 在三個 scope 可能有不同管理門檻,例如新增欄位、執行 diagnosis、解析連結就是三組已知會分歧的操作）
3. 受治理的部門表：呼叫者的房間未宣告 scope 時,預期看到**空頁而不是錯誤**;而且**永遠不要送 `acting_chatroom_id`**
4. 跨 scope 分享後保留原擁有 scope,只更新 grant 與本地可用表清單
5. 決定 **tag 怎麼切** —— 這同時決定 command 邊界與 AI 載入邊界
6. 確認「要一起原子寫入的表」全部同 scope 同 tag
