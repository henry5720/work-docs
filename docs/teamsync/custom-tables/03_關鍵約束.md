# 設計 schema 之前必須知道的硬約束

> **對象**：RD（要動手設計 schema 的人）
> **目的**：把「散在官方文件 20+ 頁、合起來才看得出來」的約束收成一頁
> **對應版本**：teamsync-backend `5.7.1`（`328f7817`）
> **撰寫日期**：2026-08-04
>
> 📖 **這頁只講「有這件事、會影響你怎麼設計」。精確的 payload、錯誤碼與數值上限一律去官方文件查**：<https://docs.customtable.teamsync.com.tw/zh-TW/>

---

## 一句話總結

**三道約束決定你的表要放哪一層,而且它們互相牽動:**

```
① LINK 只能向上
② Command 綁死在一個 scope-local tag
③ Tag 同時是「表分組 + command 邊界 + AI 載入單位」
        ↓ 三條合起來
「該一起被同一個動作寫入的表,必須同 scope 同 tag」
```

這個結論在官方文件裡沒有任何一頁直接寫出來,因為它是三頁的交集。

---

## 1. LINK 只能向上

> `src/crud/custom_table_links.py` → `validate_link_scope()`

```
       company（最廣）
          ▲
          │ 可以 link
     department
          ▲
          │ 可以 link
      chatroom（最窄）
```

目標表必須與來源表**完全同 scope**,或在**同一間公司內的更廣 scope**。向下（department → chatroom）、平行（chatroom A → chatroom B）、跨公司,一律拒絕。

**設計含意**：主檔放上層、交易資料放下層,link 方向是對的 ✅ —— 但下一條會推翻這個直覺。

---

## 2. Command 綁死在一個 scope-local tag

> `src/crud/custom_table_commands/tags.py` 的模組 docstring 講得最清楚：
> *"A command belongs to exactly one scope-local tag and may reference only live tables assigned to that tag."*

而 tag 是 **scope-local** 的 → **command 無法跨 scope**。

### 這就是為什麼「主檔往上、交易往下」會撞牆

```
chatroom scope   : 案件
department scope : 時段、班表、建案、業務

link 方向合法（案件 → 時段，向上）✅

但「認領」= 更新時段(佔位) + 更新案件(填負責人)，必須同時成功或同時失敗
      ↓
   command 只能綁一個 scope-local tag
      ↓
   時段在 department、案件在 chatroom  →  被拒絕
```

沒有原子性 → 兩個人同時按「認領」,會搶到同一個時段。

### ✅ 所以真正的準則是

> **凡是要被同一支 command 一起寫入的表,必須同 scope、同 tag。**
>
> 這條 **勝過**「主檔往上、交易往下」的直覺。

實務上通常意味著：**整個系統的表全部放 department scope**,再 grant 給聊天室。理由見 [04_Scope.md](04_Scope.md)。

---

## 3. Tag 是三合一的邊界

Tag 不只是「整理表的資料夾」：

```
            ┌──────────────┐
            │     Tag      │
            └──────┬───────┘
      ┌────────────┼────────────┐
      ▼            ▼            ▼
  表的分組    command 邊界   AI 載入單位
                            （Insight system）
```

**所以 tag 怎麼切,是整個設計裡最重要的一個決定。** 切錯了 command 寫不出來,或者 AI 的載入範圍不對。

AI 那一側的完整機制（四層開關）見 [05_AI存取的四層.md](05_AI存取的四層.md)。

## 4. 欄位的真名不是你看到的名字

顯示名稱只是別名 —— 這是為了支援「改名不會破壞既有設定」。真正的鍵是內部的 `col_<hex>`。

**影響**：filter、sort 這類地方要用內部鍵,而 saved view 的「要顯示哪些欄位」用顯示名稱。**同一份設定裡兩種形式混用是正常的,不是 bug。**

更麻煩的是 trigger 的回顯會**同時**出現兩種形式（一部分是宿主表的顯示名、一部分是目標表的內部鍵）。所以設定 UI **不能假設回顯裡每個欄位參照都是顯示名稱**。

> 哪個欄位用哪種形式 → [column-identity](https://docs.customtable.teamsync.com.tw/zh-TW/concepts/column-identity)

## 5. Rules：先知道有哪些,別背細節

> 完整 payload 與錯誤模型：[concepts/rules](https://docs.customtable.teamsync.com.tw/zh-TW/concepts/rules)

| 你想表達的 | 用哪條 rule |
| :--- | :--- |
| 這個欄位必填（可以是「符合某條件時才必填」） | `require` |
| 這幾個欄位的組合不可重複 | `unique`（由 DB 約束,擋得住併發） |
| 值域檢查（金額不可為負、代碼格式） | `check` |
| 兩個欄位的關係（結束不得早於開始） | `compare` |
| 狀態只能沿允許的路徑走 | `transition`（allowlist,不是黑名單） |
| 一旦送出／過帳,這個欄位就不能再改 | `immutable_when` |
| 同一個人／同一間會議室的時段不可重疊 | `no_overlap` |
| 另一張表必須／不得存在符合的資料 | `exists` / `not_exists` |
| 超過某金額要主管簽核 | `require_approval` |
| 同一張部門表,不同聊天室看不同列 | `channel`（SCP） |
| 不論從哪個入口寫,都必須符合的底線 | `invariant` |

### 兩個容易誤判的地方

**① 大多數 rule 可以帶條件（`when`），但有五種不行。**
其中最反直覺的是 `immutable_when` —— 它用的是「寫入**之前**的資料」來判斷。因為如果用寫入後的資料判斷,呼叫者只要在同一筆請求裡「解鎖 + 修改」,鎖就永遠不會生效。

**② `when` 只能看普通欄位,不能看 link / rollup / lookup / formula。** 計算欄位在很多地方都不能用（不只 `when`），這是設計 schema 時最常撞到的一類限制。

## 6. 排班／預約:平台有內建的一整套,不要自己刻

如果你要做「班表 → 可預約時段 → 有人認領」,平台有三件套：

```
班表表（每週樣板 + 特定日期例外）
    │
    │  每日排程掃描（materialize_slots trigger）
    ▼
時段表（每個人 × 日期 × 起始時間 一列）
    │
    ├─ unique(日期, 開始, 人) ← 讓併發認領不會撞車，也讓掃描可自我修復
    └─ no_overlap            ← 防衝堂
```

**你只宣告一次「每週怎麼排班」,每日掃描會自動維持未來一段時間的具體時段列。** 不需要手動插入任何時段,也不需要自己寫排程程式。

> 完整參數與 13 個地雷（含 horizon 的 off-by-one、1000 列上限、不能指向簽核表…）→
> [triggers/materialize-slots](https://docs.customtable.teamsync.com.tw/zh-TW/concepts/triggers/materialize-slots)
> 從零做完一套的範例 → [use-cases/booking](https://docs.customtable.teamsync.com.tw/zh-TW/use-cases/booking)

### 三個方向性警告（細節去官方文件確認)

- **時段掃描只會新增,從不修改或刪除。** 改了班表不會動到已經產生的未來時段 —— 過時的要人工取消
- **已取消的時段不會被重新掃描復活。** 取消掉就是取消掉了
- **時段表不能掛簽核規則。** 否則每日掃描都會死在簽核關卡（設定時就會被擋）

---

## 7. 簽核與 command 的交互:只掛主檔

`require_approval` 命中時,寫入不會生效,而是變成「暫存變更」等人審。**live 資料保持原狀。**

⚠️ **一支 command 只能觸及「一張」有簽核規則的表。** 超過一張直接被拒絕。

**設計含意**：報價單 + 明細這種結構,簽核規則 **只掛主檔,不要也掛明細**。否則「建立報價單」這支 command 一執行就爆。

> 完整流程與回應格式 → [concepts/approval-overview](https://docs.customtable.teamsync.com.tw/zh-TW/concepts/approval-overview)
