# 空檔推播 — 開發現況與取捨

> **給誰看**：PM 與需求方。這份只講「做了什麼、沒做什麼、為什麼跟 prototype 不一樣」，
> 不講程式。
>
> **位置**：用戶管理（`/user`）→ 右上「群發訊息」按鈕（目前只有 Vivispa 開啟）
>
> **對照的 prototype**：同目錄的 [`空檔推播_prototype.html`](./空檔推播_prototype.html)
>
> **現在的狀態**：畫面與空檔偵測都可以實際操作了，但**按下發送不會真的寄出訊息**。
> 詳見 §4。

---

## 1. 一句話說明現在能做到什麼

打開群發訊息 → 系統自動列出今天店裡「排得下療程」的空檔（預設全勾）→ 選要發給哪些標籤
的客戶 → 編輯文字、插入變數 → 按發送會看到「將要發出什麼」的完整明細，但**不會真的送**。

---

## 2. 已完成的功能

| 功能         | 說明                                                                                                                             |
| :----------- | :------------------------------------------------------------------------------------------------------------------------------- |
| 用戶標籤篩選 | 標籤直接取自用戶管理模組既有的標籤群組，新增的群組／標籤會自動出現。**用樹狀選單，群組展開就是它底下的標籤，勾群組＝全選該群組** |
| 空檔自動偵測 | 依店家營業時間、美療師班表、請假、當日預約自動推導，**已扣掉現在之前的時間**                                                     |
| 空檔預設全勾 | 不想發的取消勾選即可                                                                                                             |
| 多店查詢     | 平台角色可一次選多家店（含「全部店家」），**每家店的空檔各自分開列、各自發一輪**                                                 |
| 變數泡泡     | 可插入「名稱」與「空檔時段」                                                                                                     |
| 發送前明細   | 會列出總則數、發送對象、符合標籤的用戶名單、每一則的完整內容與字數                                                               |

標籤選單長什麼樣、為什麼是這個樣子，見 §3.6。

### 發送前明細會顯示什麼

- **摘要**：會發幾則、發送對象、渠道與字數上限、發送時機、多標籤是 OR（符合任一即發送）、
  每家店查了幾位美療師
- **符合標籤的用戶名單**（⚠️ 不等於實際收得到的人，見 §4.3）
- **逐則內容**：店名、空檔時段、字數，以及送出去的實際文字

### 店家選擇（只有平台／總部帳號會看到）

店長帳號只有自己一家，不會出現這個選單。總部帳號預設跟著用戶列表上的「篩選店家」走；
沒篩的話要自己選，**「全部店家」不會預設勾選** —— 全選會一次去查每一家店的班表，
店數多時要等，而多數情況只想發其中一家。

### 空檔怎麼算的（白話）

```
店家今天營業時間
  ∩ 這位美療師今天的班表
  − 她請的假
  − 她今天已被預約的時段
  − 現在之前的時間（下午三點打開，不會出現早上的空檔）
  ＝ 她今天的空檔候選
  → 只留下「排得下她自己療程」的那幾段
  → 多位美療師的空檔合併去重 ＝ 畫面上列出的清單
```

**多位美療師的空檔會合併成一條。** 因為訊息不會提美療師姓名，對客人來說「這段有空」就
是一件事，同一段時間發兩則只是騷擾。

**但合併只在同一家店內。** 選了多家店時，每家店的空檔各自分開列、各自發一輪 —— 訊息裡
只有時間沒有店名，把台北店的空檔發給台中店的客人就是錯的資訊。

## 3. 跟 prototype 不一致的地方，以及為什麼

### 3.1 沒有「訊息範本」區塊

**原因**：範本要能新增／編輯／刪除、還要存標籤設定，這需要後端提供儲存的地方，目前尚未
確認支援。

**影響**：prototype 右側「最快 3 個動作完成」那個價值主張**整個依賴範本**，沒有範本就
不成立。目前每次都要確認一次文字內容（有預設文案，不用從零打）。

**需要 PM 協助**：跟後端確認範本要存在哪裡、一個店能存幾份、是否需要跨店共用。

### 3.2 空檔門檻不是固定的 90 分鐘

規格寫「美療師連續 **≥90 分鐘**無預約 = 空檔」。實作改成 **≥ 該美療師最短的療程長度**。

**原因**：系統裡本來就有每個療程的實際時長，而 90 這個數字在系統裡找不到依據。用固定
90 會兩頭錯：

| 情況                     | 用固定 90 的後果                                             |
| :----------------------- | :----------------------------------------------------------- |
| 店裡最短療程 **60 分鐘** | 60–89 分鐘的空檔被藏起來 —— 那些是**約得到的**時段，白白少賺 |
| 店裡有 **120 分鐘**療程  | 90–119 分鐘的空檔會推出去，客人點進來**約不到**              |

**要 PM 確認**：這個 90 是「大概抓一個保守的數」，還是**行銷決定**（只想推 90 分鐘以上
的長療程）？如果是後者，那我改錯了方向，要改回固定 90（改動很小）。

> 附註：如果某位美療師的療程完全沒設定時長，系統會退回用 90 分鐘估算，並在畫面上標示
> 「有 N 位美療師的療程未設定時長」。看到這個提示代表**療程資料需要補**。

### 3.3 「發送時機」目前只有立即發送

**原因**：依開發指示先做立即發送。排程的底層能力（後端與共用程式）都還在，要加回來很快。

### 3.4 字數上限不是 1000

prototype 顯示 `0 / 1000`。**LINE 的實際上限是 5000 字**，1000 是 Instagram 的限制。
目前只做 LINE，所以顯示 5000。

### 3.5 兩顆變數泡泡改成不同顏色

prototype 兩顆都是綠色。實際上它們是**兩種不同的東西**：

| 泡泡                 | 誰代入           | 結果                           |
| :------------------- | :--------------- | :----------------------------- |
| **名稱**（綠）       | 系統逐位客戶代入 | 一則訊息，每個人看到自己的名字 |
| **空檔時段**（琥珀） | 發送前就地代入   | **勾 N 個時段就會發 N 則訊息** |

做成一樣的顏色，使用者無法理解為何一個能個人化、一個不能。

### 3.6 標籤改成樹狀選單（prototype 沒有這個控件）

prototype 裡的標籤是**已經填好的 chip**（例如「預約行為：被動型」），不是一個可以操作的
選單 —— 因為那份設計假設**範本會自動帶入標籤**，使用者不需要自己選。

範本這一輪沒做（§3.1），所以必須有一個真的選取控件，而 prototype 沒有提供樣子。目前用
樹狀選單：

```
[ 選擇標籤（可勾群組全選） ▾ ]
  ▸ ☐ 來源
  ▸ ☑ 消費力          ← 勾群組會連帶勾底下全部
      ☑ 高消費
```

順帶一提，prototype 那個 chip 標示是「**群組：標籤**」的複合寫法，代表群組資訊本來就該
看得見。樹狀選單把群組做成父節點，剛好把這個意圖用結構表達出來。

### 3.7 「空檔時段」用直列清單，不是橫排標籤

**原因**：互動是「預設全勾 → 掃一眼 → 取消例外」。新格式 `8/13 18:00 ~ 20:00` 有 17 個
字，橫排一行放不到兩個；而且下拉選單會把已選項折成「+3」，正好藏起每天唯一需要人工確認
的東西。

## 4. ⚠️ 還不能真的發送 —— 缺什麼

目前按「發送」只會顯示明細。要真的送出，還有三件事要處理，**按依賴順序**：

### 4.1 權限確認（最優先，會決定後面兩項要不要做）

發送必須經過 teamsync 的群發引擎，而它要求操作者對該 LINE 官方帳號有管理權限。
**店長帳號在用戶管理頁不一定滿足這個條件。**

如果不滿足 → 整個發送方式要換成另一條路（由 E-commerce 端代發），前面關於標籤對照的
討論就都不適用了。

**這件事需要跟後端確認，是目前最大的未知。**

### 4.2 標籤對照

用戶管理的標籤與 LINE 群發使用的標籤是**同一批標籤的兩份副本**（系統每分鐘自動同步）。
發送時要把前者對到後者，目前缺一個對照方式。

**已知限制**：如果兩個不同標籤群組裡有**同名標籤**（例如「來源／熟客」和「消費力／熟客」），
系統無法區分，發送對象會包含兩者。**畫面上已經會出現黃色警示告知**，但無法避免。
若要精確區分，需要後端提供對照用的接口。

**建議 PM 順便確認**：標籤命名上是否可以要求「不同群組不要取同名」，這樣就完全不會遇到。

### 4.3 名單只到「受眾」這一層

確認頁的「符合標籤的用戶」是**符合標籤的用戶名單**，不等於實際收得到訊息的人：

- 名單裡**沒綁 LINE 的收不到**（這支查詢不回傳綁定資訊）
- 送出時系統還會排除：黑名單、已封鎖官方帳號、綁到已解除連結的官方帳號

所以**不要把這個數字當成觸及人數**。真正的收件人清單要等 4.2 解決後才拿得到。

## 6. 需要 PM 回覆 / 決定的事

依重要性排序：

1. **一個時段發一則，還是一則列出所有時段？**
   目前是前者 —— 勾三個時段，同一位客人會收到**三則** LINE 訊息。
   一天連續三則推播有被封鎖的風險。
   建議改成「一則訊息列出所有空檔」，但這是產品決定。

2. **90 分鐘是怎麼來的？**（見 §3.2）是保守估計，還是行銷決定？

3. **訊息範本要不要做？** 要的話需要跟後端確認儲存方式（見 §3.1）。

4. **平台角色（總部帳號）需要用這個功能嗎？**
   空檔本質上是單店操作（某店美療師的班表）。目前總部帳號可以一次選多家店甚至全部店家，
   但**一次推多家店的實際使用情境還沒被驗證過**，而且店數越多查詢越慢。
   如果實際上只有店長會用，這條路可以整個不支援，畫面會明顯更簡單。

5. **標籤命名是否可以規範「不同群組不同名」？**（見 §4.2）

## 7. 附註：療程時長資料要補

系統用「療程實際時長」判斷空檔排不排得下。如果店家的療程沒有設定時長，畫面上會顯示
「有 N 位美療師的療程未設定時長，以 90 分鐘估算」。

看到這個提示時，代表該店的**療程資料需要補齊**，否則空檔清單會與實際可預約情況不符。
建議在正式使用前先請店家確認療程時長都有設定。
